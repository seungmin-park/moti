# 상품 정리와 구매 기록 (4a)

소유자가 실제 보관함(`/`)에서 담아둔 상품을 `/demo` 목업처럼 정리하게 하는 단위다. 상품 이름·메모·컬렉션을 고치고, 바로 구매완료로 옮긴 뒤 실행 취소하고, 구매일과 실구매가를 나중에 적고, 위시로 되돌리고, 컬렉션 이름을 바꾼다. 위시와 구매완료는 따로 본다. 모든 변경은 새로고침과 새 세션에서도 남고, 메모와 컬렉션은 어떤 구매 전환에서도 바뀌지 않는다. 이전에는 실제 화면의 상세가 읽기 전용이었고 구매 상태를 바꿀 수 없었다. DB의 `revision` 열은 있었지만 올리는 명령이 없었다.

4단위는 4a(상품 정리·구매 기록), 4b(내보내기·복원), 4c(추가 전용 공유 키)로 나눴다. 상품 삭제와 컬렉션 삭제는 목업에 없어 4a 범위가 아니다.

## 바뀐 동작

- 상품 이름은 새 열 `owner_title`에 둔다. 수집은 지금처럼 `title`만 쓰고 SQL을 바꾸지 않았다. `moti.product_json`이 `coalesce(owner_title, title)`을 `title`로 돌려주므로 응답 모양(`ProductResponse`)은 그대로다. 소유자가 고친 이름은 나중의 수집(다시 가져오기, 5단위의 매일 확인)이 지우지 못한다. 보이는 이름과 같은 이름을 보내면 아무것도 고치지 않은 것으로 보고 수집한 이름을 계속 따른다. `owner_title`도 수집한 이름과 같은 SQL 검사(1~120자, 앞뒤 공백·제어 문자 없음, NFC)를 `moti.is_clean_title`로 받는다.
- `revision`은 "커밋된 소유자 변경"의 수다. 저장된 값을 실제로 바꾸는 소유자 변경만 1 올리고 `updated_at`을 바꾼다. 링크 저장과 수집의 맡기·완료·실패·재시도는 올리지 않으므로 수집 진행이 소유자의 저장을 늦은 요청으로 만들지 않는다.
- 다섯 RPC가 의도마다 전환을 SQL에서 정한다. 모두 `moti_rpc` 소유의 보안 정의자이고 `authenticated`만 실행하며 `moti.require_owner()`를 거친다.
  - `moti_edit_product`: 이름(null이면 그대로)·메모·컬렉션 소속. 없는 컬렉션이나 다른 소유자의 컬렉션이 섞이면 `M0003`이고 아무것도 쓰지 않는다.
  - `moti_purchase_product`: 위시 → 구매완료, 구매일·실구매가는 비운다. 이미 구매완료면 바꾸지 않는다.
  - `moti_record_purchase`: 구매완료 상품의 구매일·실구매가를 쓴다. null로 지우는 것도 이 명령이다. 구매일은 1900-01-01부터 서울 기준 오늘까지, 실구매가는 0 이상 2^53−1 이하의 원(KRW)만 받는다. 빈 값(null)과 0원은 다르다.
  - `moti_return_to_wish`: 구매완료 → 위시, 구매 기록을 지운다. 이미 위시면 바꾸지 않는다.
  - `moti_rename_collection`: 만들기와 같은 이름 규칙. 다른 컬렉션과 대소문자만 다른 이름은 `M0004`, 자기 이름의 대소문자만 바꾸는 것은 받는다.
- 모든 RPC의 검사 순서는 입력(`M0002`) → 대상 없음(상품 `M0006`, 컬렉션 `M0003`) → 같은 값 → 오래된 revision(`M0008`, 새 코드) → 쓰기다. 지금 저장된 값에 적용해도 바뀌는 것이 없으면 보낸 revision과 상관없이 지금 값을 돌려주고 revision을 올리지 않는다. 두 번 누른 저장, 다시 보낸 요청, 두 번 누른 실행 취소가 해가 없다. 지금 revision으로 위시 상품의 구매 기록을 보내면 상태를 본 클라이언트의 잘못된 요청이므로 `M0002`(400)다.
- 잠금은 상품 행(또는 컬렉션 행) 하나뿐이고 수집 작업 행은 잠그지 않는다. `settling_product`의 작업 → 상품 순서와 순환하지 않는다. 소유자 변경이 쓰는 열(이름·메모·소속·구매)과 수집이 쓰는 열이 겹치지 않아 두 쓰기가 모두 반영된다.
- HTTP는 자원마다 경로 하나다. `PATCH /api/products/{productId}`는 `ProductChangeRequest { revision, change }`를 받고 `change.type`은 `details`·`purchase`·`purchase.record`·`wish`다. `PATCH /api/collections/{collectionId}`는 `CollectionRenameRequest { revision, name }`을 받는다. 기존 쓰기 경계(같은 출처, JSON, 16KiB, `no-store`)를 그대로 쓴다. 상태는 200, 400 `invalid_input`(필드 `title`·`note`·`collection`·`date`·`price`), 401·403·503, 404 `product_missing`, 409 `revision_conflict`·`collection_duplicate`, 413, 415, 422 `collection_missing`이다. 서버는 구매일을 자기 서울 날짜로 다시 검사한다. `docs/api/openapi.json`을 다시 생성했다.
- 이름·메모·구매일·실구매가 규칙은 순수 모듈 `src/features/wishlist/product-fields.ts` 하나다. 화면은 보내기 전에, 서버 명령(`application/commands.ts`)은 받은 뒤에 같은 함수로 검사하고 DB는 마지막 선으로 같은 한도를 둔다. 수집의 `cleanTitle`도 같은 정리 함수(`normalizeTitle`)를 쓴다. 수집 이름 테스트는 바꾸지 않고 통과했다. 메모는 적은 그대로(앞뒤 공백·줄바꿈 포함) 저장하고 3,000자와 NUL만 거절한다. 컬렉션 이름 바꾸기는 기존 `collection-name.ts`를 쓴다.
- 저장소 어댑터는 `ProductChange["type"]`마다 RPC 이름과 인자를 만드는 표 하나로 네 변경을 보낸다. `M0008`은 `revision_conflict`, 날짜·숫자 범위 오류(`22003`·`22007`·`22008`)는 `invalid_input`으로 바꾼다.
- 화면은 목업처럼 "위시리스트 / 구매완료" 보기를 사이드바와 모바일 하단에 둔다. 컬렉션 거르기와 함께 쓰고 개수·제목·빈 상태가 보기를 따른다. 보기와 거르기는 화면 안의 상태라 새로고침하면 위시리스트 전체로 돌아간다.
- 위시 카드에 "구매완료로 이동" 버튼이 있다. 상세의 "구매완료로 이동"과 "위시로 되돌리기"는 목업처럼 상세를 닫고 알림을 띄운다. 구매 알림 "구매완료 목록으로 옮겼어요"에는 "실행 취소"가 있다. 실행 취소는 구매 응답이 준 revision으로 `wish`를 보낸다. 상품의 revision이 알림의 revision과 같을 때만 실행 취소를 보인다(따로 저장하지 않고 계산한다). 알림은 중립 차콜 배경의 `role="status"` 영역이고 시간 제한이 없다. 닫기, 다음 쓰기, 대화상자 열기, 보기·거르기 변경, 상품 revision 변경에서 사라진다.
- 구매완료 카드는 마지막 확인 가격 대신 실구매가를 보인다. 기록이 없으면 "실구매가 미입력", 0원이면 "₩0"과 "실구매가"이고 구매일이 있으면 "실구매가 · 2026. 11. 01. 구매"처럼 함께 적는다.
- 상세는 목업의 상세를 따른다. 읽기 정보, 이름·메모·컬렉션 체크 상자와 "변경사항 저장"(바뀐 칸이 있을 때만 켜짐), 구매완료 상품의 구매 기록 칸(구매일 `type="date"`, `max`는 서울 기준 오늘, 숫자 실구매가와 "원", "구매 정보 저장"), 그리고 "구매완료로 이동" 또는 "위시로 되돌리기"가 있다. 초안은 손댄 칸만 들고 각 칸은 `초안 ?? 지금 값`을 보인다. 손대지 않은 칸은 수집 결과와 다시 읽은 값을 따로 맞추지 않아도 따라간다.
- 쓰기는 한 번에 하나다. 쓰기나 전체 다시 읽기가 진행 중이면 쓰는 버튼이 모두 꺼진다.
- 쓰기 응답과 전체 읽기는 순수 `mergeProduct`로 revision을 비교해 합친다. 높은 revision은 상품을 바꾸고, 같은 revision은 더 나아간 수집 진행만 받고, 낮은 revision은 버린다. 주기적 다시 읽기(poll)는 지금처럼 수집 진행만 합치되, 화면보다 낮은 revision의 결과는 버린다. 저장 전에 시작한 읽기가 이전 값을 되돌리지 못한다.
- 409 `revision_conflict`를 받으면 보관함을 다시 읽고 손댄 초안은 지키며 상세에 "다른 곳에서 먼저 바뀌었어요. 최신 내용을 불러왔어요. 확인 후 다시 저장해 주세요."를 보인다. 카드나 알림에서 한 쓰기의 충돌은 같은 문구를 알림으로 보인다.
- 컬렉션을 고르면 제목 옆 연필 버튼 "컬렉션 이름 바꾸기"가 같은 컬렉션 대화상자를 이름 바꾸기 모드("이름 저장")로 연다. 이름이 그대로면 호출 없이 닫고, 다른 컬렉션과 대소문자만 다른 이름은 보내기 전에 거절한다. 바꾼 컬렉션은 자리·소속 상품·거르기를 유지하고 "컬렉션 이름을 바꿨어요" 알림을 띄운다.
- 선택된 보기·포커스는 흰색·중립 회색·차콜만 쓴다. 초록·세이지는 없다.

## 설계 선택

| 기준 | A. 의도별 명령과 SQL 전환 | B. 상품 하나의 정리 문서를 비교 후 저장 |
| --- | --- | --- |
| 쓰기 경로 | 의도마다 POST 경로·RPC·DTO 6쌍, 새 오류 코드 2개(`revision_conflict`, `purchase_state_conflict`) | 자원마다 PUT 경로 하나, RPC 2개, 새 오류 코드 1개 |
| "구매 전환은 메모·컬렉션을 바꾸지 않는다" | SQL이 의도별로 보장 | 화면과 서버가 함께 쓰는 순수 모듈이 다음 문서를 계산하고, DB는 의도를 모름 |
| 실행 취소 | 구매가 발급한 토큰(`purchase_revision` 열). 메모를 고친 뒤에도 유효 | 알림의 revision을 기준으로 위시 복원 |
| 응답 모양 | `ProductResponse` 그대로 | `collectedTitle`과 `curation`으로 바꿈, 약 10개 파일 기계적 변경 |
| 같은 값 다시 보내기 | revision이 달라 409 후 다시 읽기 | 200, revision 그대로 |
| 상세 초안 | 바뀐 상품에 초안을 다시 맞추는 `rebaseDetail` | 손댄 칸만 초안에 둠 |
| 요청 크기 | 의도에 필요한 값만 | 한 번의 구매에도 메모 전체(최악 16,558바이트로 16KiB 초과) |

A를 바탕으로 B의 장점을 옮겼다.

- 전환은 A처럼 SQL이 의도별로 정한다. "메모와 컬렉션은 모든 구매 전환에서 남는다"를 각 클라이언트의 계산이 아니라 서버의 보장으로 둔다. B가 꼽은 가장 큰 위험이었고, 4c의 공유 키 클라이언트와 4b의 복원이 화면 논리에 기대지 않게 한다.
- 경로는 B처럼 자원마다 하나(PATCH)이고 본문의 `change.type`이 A의 의도를 고른다. 자원마다 파싱·충돌·오류 대응을 처리하는 곳이 하나다. 6쌍의 경로·DTO·화면 오류 표를 만들지 않는다.
- 같은 값은 B처럼 revision과 상관없이 200이다.
- 실행 취소에 새 열을 두지 않는다. 구매 응답의 revision으로 `wish`를 보내고 화면은 revision이 같을 때만 실행 취소를 보인다. A의 토큰 열은 "구매 뒤 메모를 고친 다음 실행 취소"를 위한 상태인데, 이 경우는 상세의 "위시로 되돌리기"가 같은 결과를 준다. `purchase_state_conflict`도 필요 없어졌다. 목업과의 차이는 아래 "남은 범위"에 적었다.
- 지금 revision으로 보낸 불가능한 전환(위시 상품의 구매 기록)은 새 코드 대신 `invalid_input`이다.
- 응답 모양은 A처럼 그대로 둔다. 화면과 테스트를 대량으로 바꾸지 않는다.
- 상세 초안은 B처럼 손댄 칸만 둔다. `rebaseDetail`이 없다.

두 후보는 같은 모델 계열에서 독립적으로 작성했고 조정자가 합쳤다. 다른 계열 심사는 제공되지 않아 생략했다.

구현은 합친 설계를 따랐고 다음은 설계 문서와 다르다.

- 화면의 `writing`은 상품 쓰기(`{ productId, intent }`)만 담는다. 컬렉션 이름 바꾸기는 기존 컬렉션 대화상자의 `saving`으로 두 번 제출을 막는다.
- 주기적 다시 읽기는 수집 진행만 합치는 규칙을 유지하면서 화면보다 낮은 revision의 결과를 버린다.
- 이름 바꾸기 버튼은 글자 대신 접근 이름이 "컬렉션 이름 바꾸기"인 연필 아이콘이다. 구매완료 카드의 0원은 목업 카드처럼 값 "₩0"과 라벨 "실구매가"로 나눠 보인다.

CI 결과는 PR #11(https://github.com/seungmin-park/moti/pull/11)의 현재 head에서 확인한다. 실제 스택 브라우저 검사는 다섯 흐름을 두 기기에서 실행한다. 상세에서 이름·메모·컬렉션을 고친 뒤 새로고침과 새 세션의 유지, 카드에서 구매 후 실행 취소, 구매일과 0원 기록 뒤 빈 값으로 지우기, 위시로 되돌려도 남는 메모·컬렉션과 보기 전환, 소속 상품을 유지하는 컬렉션 이름 바꾸기와 중복 거절, 다른 곳에서 먼저 바뀐 상품의 충돌 안내와 입력한 메모의 유지다. 상세·이름 바꾸기 대화상자의 axe 검사와 알림·선택된 보기의 중립 색 검사도 포함한다.

각 단계의 Red는 `docs/evidence/organize/red-*.txt`에 있다.

- `red-fields.txt`: 공유 규칙 모듈이 없을 때 36개 모두 실패한다.
- `red-persistence.txt`: 4a 마이그레이션 없이 실행했다. 정리 RPC가 없어 persistence 40개가 실패하고, 공개 RPC 목록을 확인하는 보안 검사 1개가 새 RPC 다섯 개가 없어 실패한다.
- `red-commands.txt`: 상품 정리·이름 바꾸기 명령이 없을 때 27개가 실패한다.
- `red-service.txt`: 저장소의 `changeProduct`·`renameCollection`이 없을 때 service 10개가 실패한다.
- `red-handlers.txt`: 두 PATCH 처리기가 없을 때 handler 검사와 OpenAPI 일치 검사 42개가 실패한다.
- `red-http.txt`: 두 PATCH 처리기가 없을 때 실제 HTTP 4개가 실패한다. 다른 출처 PATCH의 403 검사는 기존 쓰기 경계가 처리기보다 먼저 거절해 Red 때도 통과했다. 새 경로가 그 경계를 지나는지 지키는 회귀 검사다.
- `red-screen-purchase.txt`, `red-screen-detail.txt`, `red-screen-rename.txt`: 보기·카드 구매·알림·실행 취소, 상세 수정·구매 기록·충돌, 컬렉션 이름 바꾸기를 만들기 전의 화면 상태·API 클라이언트·표시 문구 실패(34개, 22개, 11개)다.
- 실제 스택 브라우저 검사(`tests/browser/library-organize.spec.ts`)는 동작을 만든 뒤 작성해 별도 Red가 없다. 첫 실행에서 10개 중 6개가 실패했다. 알림을 보이는 `role="status"` 영역은 고정 위치 알림을 감싸기만 해서 자기 크기가 없고, Playwright는 크기 없는 요소를 보이지 않는 것으로 판단한다. 화면은 알림을 정상으로 보였고 스크린 리더 안내에도 영향이 없다. 제품 결함이 아니라 선택자 문제여서 영역 안의 `.toast`를 확인하도록 테스트를 고쳤다.

## 남은 범위

- 실행 취소는 목업과 다르다. 목업은 구매 뒤 메모를 고쳐도 실행 취소가 현재 메모와 컬렉션을 보존한다. 실제 화면은 상품의 revision이 구매 응답과 같을 때만 실행 취소를 보이고, 상세를 열면 알림이 닫힌다. 구매 뒤 메모·이름·컬렉션·구매 기록을 바꾸면 실행 취소가 사라진다. 그때는 상세의 "위시로 되돌리기"를 쓴다. 메모와 컬렉션은 남고 구매일·실구매가는 지워진다. 위시로 되돌리기는 기록한 구매 정보를 확인 없이 지운다(목업과 같음).
- 상품 삭제와 컬렉션 삭제는 목업에 없어 만들지 않았다. 사진 사본의 정리 순서(참조를 먼저 지우고 사본 삭제)는 삭제를 만들 때 정한다.
- 소유자 이름을 수집한 이름으로 되돌리는 방법이 없다. 한 번 고친 뒤에는 수집한 이름을 그대로 입력해도 소유자 이름으로 남아 이후 수집을 따르지 않는다. 목업에도 없는 기능이다.
- 4b는 `owner_title`을 내보내고 복원해야 한다. `p.title`을 바로 읽는 SQL은 보이는 이름이 아니라 수집한 이름을 얻는다. 복원 뒤 `revision`을 어떻게 둘지도 4b에서 정한다. 5단위는 `owner_title`을 쓰지 않고 구매완료 상품을 건너뛰어야 한다.
- 두 탭에서 서로 다른 칸을 고쳐도 revision이 하나라 충돌한다. 다시 읽은 뒤 한 번 더 저장하면 된다. 칸별 병합은 하지 않는다.
- 실구매가는 원(KRW)만 받는다. 마지막 확인 가격이 다른 통화여도 같다. 미래 구매일은 서버의 서울 날짜로 거절한다. 자정 무렵 기기 시계가 서버와 다르면 화면이 허용한 날짜를 서버가 거절할 수 있다.
- `screen-state.ts`가 362줄에서 660줄로 늘었다. 상세 대화상자의 전환을 별도 모듈로 나눌지는 다음 화면 변경 때 검토한다.
- 실제 Google OAuth, 실제 iPhone, Vercel과 실제 Supabase 프로젝트는 검증하지 않았다. 브라우저 검사는 로컬 Auth 세션과 iPhone 크기 WebKit이다. 배포는 별도 승인이다.
