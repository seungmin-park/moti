# iPhone 공유 단축어의 추가 전용 키 (4c)

소유자가 Safari나 쇼핑 앱의 공유 메뉴에서 단축어를 골라 상품 링크를 moti에 담는 단위다. moti를 열거나 단축어에서 로그인하지 않아도 된다. 단축어가 쓰는 저장 키는 링크를 더하는 일만 할 수 있다. 보관함 읽기·고치기·지우기·내보내기·복원과 키 관리는 할 수 없다. 키는 해시로만 저장하고, 실제 화면에서 언제든 바꾸거나 폐기한다. 키와 Google 세션은 서로를 대신하지 않는다. 이전에는 공유 저장이 목업의 체험 화면에만 있었다.

## 바뀐 동작

- 마이그레이션 `20261116000000_share_keys.sql` 하나에 이 단위의 SQL이 있다.
  - 링크를 상품과 첫 수집 작업으로 만드는 규칙을 `moti.add_link`(호출자 권한으로 실행) 하나로 모았다. `moti_save_link`는 서명·오류 순서·결과를 그대로 두고 컬렉션 검사 뒤 이 함수를 부른다. 기존 persistence·service·HTTP·브라우저 검사가 그대로 통과했다. 링크 검사도 `moti.is_link_input` 하나다.
  - `moti.share_keys`는 키마다 SHA-256(`token_hash`), 끝 네 글자(`hint`), 만든·마지막으로 담은·폐기한 시각, 한 시간 사용 창을 둔다. 부분 고유 인덱스로 소유자당 활성 키는 하나다. 폐기한 행은 남아 화면이 언제 폐기했는지 보인다. 백업과 복원은 이 테이블을 건드리지 않는다.
  - 소유자 RPC 세 개(`moti_rpc` 소유, `authenticated`만, `require_owner`)가 있다. `moti_share_key_read`는 활성 키, 없으면 마지막으로 폐기한 키, 없으면 null을 돌려준다. `moti_share_key_issue(p_replaces)`는 화면이 본 활성 키(없었으면 null)가 지금 활성 키일 때만 그 키를 폐기하고 새 키를 만든다. 아니면 `M0008`이다. 동시에 만든 두 요청도 하나만 커밋한다. 비밀은 SQL에서 `moti_sk_`와 `gen_random_bytes(32)`의 base64url 43자로 만들고 이 응답에만 담는다. `moti_share_key_revoke(p_key_id)`는 멱등이고 처음 폐기한 시각을 지킨다. 소유자에게 없는 키는 `M0011`이다. `moti_rpc`는 해시와 사용 창 열을 읽지 못한다.
  - 새 역할 `moti_share`(로그인 불가, 상속 없음, RLS 우회 없음)가 익명이 실행하는 유일한 함수 `public.moti_share_add`를 소유한다. 이 역할의 권한은 catalog 테스트가 정확한 목록으로 고정한다. 소유자 설정의 두 열 읽기, 자기 활성 키 찾기와 사용 기록, 중복 확인에 필요한 상품 여섯 열 읽기, 상품 다섯 열과 첫 작업 세 열 넣기, 링크 추가·소유자 확인 함수와 테이블 검사 제약이 부르는 함수 실행이다. 갱신·삭제, 컬렉션·소속·Storage, 다른 함수는 없다. `authenticated`는 이 함수를 실행하지 못한다.
  - `moti_share_add(p_key, …링크…)`는 `{kind}`(`added`·`duplicate`)만 돌려준다. 형식이 다르거나 모르거나 폐기했거나 소유자 설정이 바뀐 키는 모두 같은 경로로 같은 `M0009`·같은 문구다. 한 키는 사용 창의 첫 사용부터 한 시간에 30번 담는다(이미 담은 링크도 센다). 31번째는 `M0010`이고 아무것도 바꾸지 않는다. 거절된 호출은 함께 되돌아가 사용 횟수와 마지막 사용 시각을 바꾸지 않는다. 검사를 지난 값을 테이블이 거절하면 행 내용이 익명에게 가지 않도록 `M0002`로 바꾼다. 폐기는 진행 중인 담기의 행 잠금을 기다리므로 폐기가 끝난 뒤에는 그 키로 담을 수 없다.
  - `moti_metadata_wake(p_limit)`은 지금 세대에서 아직 한 번도 시작하지 않은 대기 작업을 최신 상품부터 1~8개 골라 대기열 앞에 다시 두고(`updated_at`) 그 상품을 돌려준다. 다른 요청이 잠근 작업은 건너뛴다(`skip locked`). 작업만 잠가 작업 → 상품 잠금 순서를 지킨다.
- 단축어 경로는 `POST /api/share/links`다. `Authorization: Bearer moti_sk_<43자>`와 `{"url"}` JSON(8KiB 이하, 다른 칸 거절)을 받는다. 처리 순서는 키 형식(본문을 읽기 전), 설정, 본문, `parseLink(url, "")`, `moti_share_add`다. 조립 위치 `src/app/_server/share-context.ts`는 쿠키를 읽지도 쓰지도 않는 익명 클라이언트를 만든다. ESLint가 이 파일과 경로에서 `next/headers`·`@supabase/ssr`·쿠키 컨텍스트를 막는다. 응답마다 단축어가 보여줄 한국어 `message`, `no-store`가 있고 쿠키와 CORS 허용 헤더는 없다. 출처는 묻지 않는다. 키는 URL에 넣지 않는다.

  | 경우 | 상태·코드 | message |
  | --- | --- | --- |
  | 새로 담음 | 201 `added` | 위시에 담았어요. 상품 정보는 moti를 열면 가져와요. |
  | 이미 담음 | 200 `duplicate` | 이미 담아둔 상품이에요. |
  | url 하나가 아닌 본문, 상품 링크가 아님 | 400 `invalid_link` | 상품 링크를 찾지 못했어요. 상품 페이지에서 다시 공유해 주세요. |
  | 키 없음·형식 다름·모름·폐기(같은 바이트, `WWW-Authenticate: Bearer`) | 401 `share_key_rejected` | 저장 키가 맞지 않거나 폐기됐어요. moti의 공유 저장 화면에서 새 키를 만들어 단축어에 넣어 주세요. |
  | 한 시간 30번 | 429 `share_key_busy` | 한 시간에 30번까지 담을 수 있어요. 잠시 뒤 다시 공유해 주세요. |
  | JSON 아님·8KiB 초과 | 415·413 | 단축어 설정을 확인해 주세요… / 공유한 내용이 너무 길어요. |
  | 판별 충돌 | 409 `identity_conflict` | 같은 링크를 확인하지 못했어요. 다시 공유해 주세요. |
  | 설정 없음·저장소·연결 | 503 `unconfigured`·`unavailable` | 지금은 moti에 담지 못했어요. 잠시 뒤 다시 공유해 주세요. |
- 소유자 경로는 기존 보관함 관문(쓰기는 같은 출처, 세션, Google 소유자)을 지난다. `GET /api/share-keys`는 키의 끝 네 글자와 시각, `POST /api/share-keys { replaces }`는 201 `{ key, secret }`(`no-store`), 오래된 화면은 409 `revision_conflict`, `DELETE /api/share-keys/{keyId}`는 200 폐기한 키, 없는 키는 404 `share_key_missing`(새 오류 코드)이다. 키만 보내고 쿠키가 없는 요청은 모든 소유자 경로에서 401 `signed_out`이다.
- `POST /api/library/metadata`(본문 `{}`)는 깨운 상품을 202로 돌려주고 응답 뒤에 두 개씩, 40초가 지나면 새로 시작하지 않고 수집한다. 화면은 보관함을 처음 받았을 때(뒤로 가기 캐시에서 돌아온 경우 포함) 시도 0인 대기 상품이 있으면 한 번 부르고, 답을 revision 규칙으로 합친 뒤 다시 읽기를 짧은 간격부터 시작한다. 실패는 알리지 않는다. 키로 담은 상품, 4b의 40초 창을 넘긴 복원 상품, 응답 뒤 수집이 시작조차 못 한 웹 저장이 이렇게 깨어난다.
- 실제 화면에 "공유 저장" 보기가 생겼다. PC 사이드바와 모바일 하단 탐색에 목업과 같은 이름과 아이콘으로 있다. 목업의 머리말·세 단계를 쓰고, 체험 버튼·휴대폰 미리보기·예시 결과는 예시 데이터라 넣지 않았다.
  - 1단계에 단축어를 손으로 만드는 다섯 동작과 이 배포의 주소(`/api/share/links`, 비밀 아님)와 "주소 복사"가 있다. 동작 이름은 기기에서 확인하지 않았다고 화면에도 적었다. 3단계는 단축어가 보여줄 메시지를 경로의 문구 그대로 나열한다.
  - 저장 키 패널은 키 없음("아직 저장 키가 없어요." → 저장 키 만들기), 한 번 보이는 키(`Bearer moti_sk_…`를 고를 수 있는 글자로, "헤더 값 복사", "이 키는 지금 한 번만 보여요…", "붙여 넣었어요"), 활성 키("저장 키 ••••a1B2 · 11월 13일 만듦"과 "아직 이 키를 쓴 적이 없어요." 또는 "마지막으로 이 키를 쓴 때: 11월 13일 오후 2:04", 새 키로 바꾸기·키 폐기), 폐기한 키("이전 키(••••a1B2)는 11월 13일에 폐기했어요.")를 보인다. "연결됨", "연결 완료", "설치 완료"는 어디에도 없다. 마지막으로 쓴 때(새로 담았거나 이미 담긴 링크였을 때)만 증거로 보이고 그렇게 이름 붙였다. 폐기에 성공하면 키를 다시 읽어, 다른 기기가 먼저 바꾼 새 키가 활성이면 그 키를 보인다.
  - 바꾸기와 폐기는 패널 안의 확인 영역(`role="group"`)이 묻는다. "취소"에 초점이 가고 Esc로 닫으며 닫으면 연 버튼으로 초점이 돌아간다. 키가 나타나면 "헤더 값 복사"에, 사라지면 패널의 첫 버튼에 초점을 둬 초점이 패널 밖으로 사라지지 않는다. 409·404와 결과를 모르는 실패는 키를 다시 읽어 실제 상태를 보이고 안내를 남긴다.
  - 비밀은 화면 상태에만 있고 "붙여 넣었어요", 보기 바꾸기, 뒤로 가기 캐시 복귀에서 사라진다. 보기를 떠난 뒤 도착한 비밀은 보이지 않는다. 보기를 열 때마다 키를 다시 읽어 마지막 사용 시각이 맞다. 컬렉션을 고르면 위시 보기로 간다.
  - 클립보드가 거절하면(보안 컨텍스트나 권한) "복사하지 못했어요. 글자를 길게 눌러 직접 복사해 주세요."를 보인다. 흰색·중립 회색·차콜만 쓰고 오류만 빨간색이다. 버튼은 44px 이상이고 키 글자는 어디서나 줄을 바꾼다.
- `docs/api/openapi.json`을 다시 생성했다. 단축어 경로는 `shareKey` bearer 보안 체계를 쓰고 다른 경로는 쿠키 세션이다.

## 설계 선택

| 기준 | A. 직접 추가 | B. 받은 링크함(inbox) |
| --- | --- | --- |
| 키의 쓰기 | 상품과 첫 수집 작업(전용 역할의 열 단위 권한) | 별도 테이블 `shared_links`에만, 보관함 테이블 권한 없음 |
| 공유 순간의 답 | 담았음·이미 담음(목업과 같음) | 보냈음만. 중복은 나중에 화면에서 |
| 같은 링크 판별 | Next의 `parseLink`가 만든 판별 주소를 SQL이 다시 검사 | 소유자 세션이 `parseLink`로 옮길 때 |
| 수집 시작 | 소유자가 화면을 열 때 깨우기 | 소유자가 화면을 열 때 옮기며 수집 |
| 키 수·이름 | 활성 하나, 이름 없음 | 활성 셋까지 |
| 추가 부분 | 테이블 하나, 역할 하나, 익명 RPC 하나, 소유자 RPC 넷, 경로 다섯 | 테이블 둘, 역할 하나, 익명 RPC 하나, 소유자 RPC 여섯, 경로 여섯, 옮기기·거절 목록 |
| 유출된 키의 힘 | 한 시간 30개 추가, 담김 여부 확인 | 한 시간 30개·대기 100개 추가, 폐기하면 대기분 삭제 |

A를 바탕으로 B의 검사와 위험 기록을 옮겼다(계약 `4c-design.md`).

- 직접 추가를 골랐다. 승인한 목업은 공유 순간에 "위시에 담았어요"·"이미 담아둔 상품이에요"·"실패해도 링크는 남아요"를 말한다. 라이브러리의 중복 판별로 직접 담아야 정직하게 말할 수 있다. 받은 링크함은 테이블·옮기기 단계·대기 상태를 더하는데, 수집 시점은 두 설계가 같다(소유자가 moti를 열 때 또는 5단위).
- 울타리는 함수 본문이 아니라 전용 역할의 권한이다. catalog 테스트가 익명이 실행하는 `moti_*` 함수가 하나뿐임과 `moti_share`의 권한 목록을 고정한다. PostgREST로 직접 불러도 같도록 키·소유자·링크 검사와 사용 창을 모두 SQL에 두었다. "익명 함수 실행은 취소한다"는 규칙에 이 예외를 이름으로 적었다(`backend-implementation.md`).
- B에서 옮긴 것. 같은 출처 `Origin`과 키만으로 모든 소유자 경로를 부르면 401 `signed_out`이고 DB가 그대로인 HTTP 검사, PostgREST에 비밀을 Bearer로 보내면 JWT가 아니라 거절되는 persistence 검사, `moti_share`로 고정 권한 밖(상품 이름·컬렉션 등)을 읽거나 쓰면 42501인 검사, 소유자 쿠키만 보낸 단축어 요청이 401이고 저장소를 부르지 않는 처리기 검사, 다른 사이트 `Origin`과 맞는 키는 받는 처리기 검사, 그리고 아래 남은 범위의 위험들이다.
- B를 고르지 않은 대가. 유출된 키는 링크가 이미 담겼는지 알 수 있고(새 링크마다 소유자에게 보이는 행이 하나 생긴다), 폐기해도 이미 담긴 상품은 남는다. 한 시간 30개로 묶었다.

두 후보는 같은 모델 계열에서 독립적으로 작성했고 조정자가 합쳤다. 다른 계열 심사는 제공되지 않아 생략했다.

구현은 합친 설계를 따랐고 다음은 설계 문서와 다르다.

- `moti_share`는 `is_collection_error`·`is_image_error`·`is_clean_title` 실행 권한도 가진다. 테이블 검사 제약은 넣는 역할의 권한으로 함수를 부르기 때문이다. persistence 검사가 "permission denied for function is_collection_error"로 보여 주었고 권한 목록 검사에 넣었다. 소유를 넘긴 뒤 `public` 스키마의 `usage`·`create`는 모두 거뒀다.
- 소유자 키 경로의 오류는 보관함 관문을 지나므로 `LibraryError`(`share_key_missing` 추가)다. 도메인 `ShareError`는 단축어 경로에만 있다(`key_rejected`·`key_busy`·`invalid_input`·`identity_conflict`·`storage_unavailable`). 서비스도 단축어용(`createShareLinkService`)과 소유자용(`createShareKeyService`)으로 나눴다. 두 경로가 다른 클라이언트(익명·소유자 세션)를 쓰기 때문이다.
- 실제 HTTP와 실제 스택 브라우저는 깨우기를 루프백 주소(`http://127.0.0.1:9/…`)로 증명한다. 앱의 가져오기 정책이 이 주소를 거절해 상품이 대기에서 "정보를 가져오지 못했어요"로 바뀐다. 운영 정책으로는 고정 페이지 서버에 닿을 수 없기 때문이다. 이름과 가격까지 채우는 경로는 service 검사가 실제 실행기와 고정 페이지(쇼핑몰만 바꿈)로 증명한다.
- 바꾸기·폐기 확인은 모달이 아니라 패널 안의 확인 영역이다. 공용 `Dialog`는 `showModal()`이 닫기 버튼에 초점을 주므로 새로 연 대화상자의 "취소"에 초점을 둘 수 없다. 패널 안이면 "취소"에 바로 초점이 가고 Esc와 초점 복귀를 직접 다룬다.
- 바꾸기·폐기의 결과를 모르는 실패(연결 끊김·503)도 키를 다시 읽는다. 답만 잃고 커밋됐을 수 있기 때문이다.
- 깨우기의 동시 실행 2개·40초는 복원과 같은 값이지만 상수(`WAKE_CONCURRENCY`, `WAKE_WINDOW_MS`)를 따로 두었다. 4b 코드를 건드리지 않으려고.
- 3단계 커밋(`9862387`)은 `share-add.test.ts`에 lint 경고 다섯 개를 남겼다. 그 커밋에서 lint를 다시 돌리지 않았다. 4단계 커밋(`c64d1c8`)에서 고쳤다.

## 검토

이 기록은 구현 담당자가 썼다. 구현에 참여하지 않은 검토자가 head `d0f4a61`의 설계 계약, 전체 diff, 이전 마이그레이션과 모든 계층의 테스트를 읽었다. 검토자는 단위 테스트 98개만 돌렸고, 실제 스택 검사는 조정자가 같은 head에서 `npm run verify`(종료 0)로 다시 확인했다.

- 병합 전에 고쳐야 할 결함은 없었다. 익명이 실행하는 함수는 `moti_share_add` 하나이고 `add_link`를 임의 소유자로 부를 경로가 없다. 거절은 고정 코드와 메시지뿐이고 폐기·모름·형식 오류가 같은 401이다. 사용 창과 폐기 경쟁은 행 잠금으로 맞고, 단축어 경로는 쿠키를 읽거나 쓰지 않으며, `moti_save_link` 리팩터는 검증 순서·오류·중복 의미를 지켰다. 깨우기는 작업만 `skip locked`로 잠가 다른 쓰기와 교착하지 않는다.
- 권고 네 건을 반영했다. catalog 검사가 `moti_share`의 구성원이 `postgres`뿐임을 단언한다(구성원이 생기면 그 역할이 권한을 그대로 쓴다). 깨우기 검사에 다시 수집으로 대기열에 돌아온 작업(시도 1회)을 넣어 `attempts = 0` 조건을 증명한다. 두 검사는 마이그레이션에 `authenticator` 구성원을 더하거나 조건을 지웠을 때 실패하는 것을 확인했다(`docs/evidence/share/red-review-*.txt`). 오래된 탭의 폐기 뒤 키를 다시 읽고, 키 사용 시각의 문구를 "이 키를 쓴 때"로 바꿨다.
- 나머지 지적(열어 둔 탭, 판별 주소 선점, 동시 사용 창 검사, 확인 영역 닫힘)은 아래 남은 범위에 적었다.

## 남은 범위

- 실제 기기에서 확인하지 않은 것. iPhone 공유 메뉴, 단축어 앱의 한국어 동작 이름과 칸, "URL 콘텐츠 가져오기"가 4xx 본문을 돌려주는지 아니면 단축어 오류로 멈추는지(본문은 언제나 `message`를 담는다), 쇼핑 앱이 공유하는 값(URL 없는 글이면 400 안내, `link.coupang.com` 같은 짧은 링크는 웹에서 담은 같은 상품과 다른 판별 주소라 중복으로 알아보지 못한다), iCloud의 단축어 동기화, 알림 모양. 브라우저 검사는 Node `fetch`로 단축어의 요청을 흉내 내므로 계약을 증명할 뿐 기기 동작을 증명하지 않는다.
- 호스팅. 프록시가 `Authorization` 헤더를 앱에 넘기는지 배포 전에 확인한다. 미리보기 배포는 주소가 다르고 배포 보호가 브라우저가 아닌 POST를 막을 수 있다. 화면의 주소는 지금 연 배포의 주소다.
- 운영 Supabase가 RPC 인자(평문 키)를 Postgres·API 로그에 남기지 않는지 확인하지 않았다(추정). 배포 전에 확인한다.
- 클립보드는 보안 컨텍스트와 권한이 필요하다. 실패하면 고를 수 있는 글자가 남는다. iOS가 복사와 붙여 넣기 사이에 Safari 탭을 버리면 비밀을 다시 볼 수 없어 새 키로 바꾼다. 주소를 먼저, 키를 마지막에 두어 앱 전환을 한 번으로 줄였다.
- 상품 삭제가 없다(로드맵 범위 밖). 유출된 키로 담긴 링크(한 시간 30개까지)는 4b 복원으로만 지울 수 있다. 폐기는 이후 추가를 막을 뿐 이미 담긴 상품을 지우지 않는다.
- 유출된 키는 링크가 이미 담겼는지 알 수 있다. 새 링크로 시험할 때마다 소유자에게 보이는 상품이 하나 생긴다.
- 모르는 키의 대량 요청은 요청마다 인덱스 조회 한 번이다. IP별 제한은 없고 호스팅 보호에 맡긴다. 키 형식만 맞으면 누구나 이 경로가 8KiB 본문을 읽게 할 수 있다(형식은 공개다). 다른 경로는 여전히 소유자 확인 뒤 읽는다.
- 키로 담은 상품은 소유자가 moti를 열 때 수집을 시작한다. 그 전까지 다른 기기에도 "정보 수집 대기"로 보인다. 깨우기는 한 번에 8개, 응답 뒤 40초다. 나머지는 다음에 열 때 깨어나고, 그 사이 60초가 지나면 멈춤으로 보였다가 다시 대기로 돌아간다.
- 깨우기는 복원 뒤 40초 창을 넘긴 상품과 응답 뒤 수집이 시작조차 못 한 웹 저장도 깨운다. 이전에는 멈춤으로 남아 "다시 가져오기"를 기다렸다. 같은 작업을 두 실행기가 노리면 `metadata_claim`의 조건부 갱신 하나만 이기고 다른 쪽은 `busy`로 끝난다.
- 5단위(정기 작업)는 공유 키를 자격으로 쓰지 않는다. 깨우기와 같은 대기 작업을 자기 자격으로 집을 수 있다.
- 키 사용 시각은 새로 담았을 때와 이미 담긴 링크였을 때 바뀌고, 거절된 요청에서는 바뀌지 않는다. 화면은 단축어가 설치됐는지 알 수 없고 그렇게 말하지 않는다.
- 열어 둔 탭은 키로 담은 상품을 바로 보이지 않는다. 화면은 처음 불러올 때와 뒤로 가기 캐시에서 돌아올 때만 깨우기를 부르고, 주기적 읽기는 이미 보이는 상품만 합친다. iPhone Safari에 moti 탭이 살아 있는 채로 단축어를 쓰고 돌아오면 새로고침해야 새 상품이 보이고 수집이 시작된다. 화면이 다시 보일 때 간격을 두고 다시 읽고 깨우는 것은 후속으로 남긴다.
- PostgREST를 직접 부르면 `parseLink`를 거치지 않아 판별 주소를 링크와 따로 정할 수 있다. 유출된 키를 가진 사람이 소유자가 나중에 담을 상품의 판별 주소를 미리 차지하면, 소유자의 웹 저장은 이미 담긴 상품으로 끝나고 공격자가 정한 링크의 행을 가리킨다. 수집기는 그 링크를 `strictFetchPolicy`로 가져온다. 두 주소의 호스트를 SQL에서 맞춰 보는 검사는 하지 않았다. 키를 폐기하고 4b 복원으로 행을 지울 수 있다.
- 사용 창(한 시간 30번)은 행 잠금으로 순서가 정해지지만 동시 요청 검사는 없다. 패널이 준비된 상태에서 다시 읽기가 끝나면 열려 있던 확인 영역이 닫힌다.
- 실제 Google OAuth와 운영 Supabase·Vercel은 검증하지 않았다. 배포는 별도 승인이다.
