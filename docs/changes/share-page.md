# Safari 단축어가 읽은 페이지로 상품 정보 채우기

소유자가 Safari에서 상품을 공유하면 단축어가 지금 열린 페이지의 머리 정보를 함께 보내고, moti가 그것으로 이름·가격·사진을 채우는 단위다. 네이버 스마트스토어, 쿠팡, G마켓은 서버 요청을 막는다(가정 회선에서도 브라우저 같은 헤더로 429·403). 그래서 이 쇼핑몰의 상품은 "정보를 가져오지 못했어요"로 남았다. 같은 페이지를 이미 보여 주고 있는 소유자의 Safari는 막히지 않는다. 이 쇼핑몰의 가격을 나중에 다시 확인하는 일은 여전히 실패한다(서버 읽기가 막혀 있다). 이 한계는 받아들였다.

## 바뀐 동작

- 단축어 스크립트 `src/features/share/shortcut/page-snapshot-script.ts`(`PAGE_SNAPSHOT_SCRIPT`)
  - 소유자가 "웹 페이지에서 JavaScript 실행"에 붙여 넣는 글이다. 화면이 같은 글을 보이고 "스크립트 복사"로 복사한다.
  - 보내는 것은 서버가 쓰는 것뿐이다. `location.href`, `document.title`, 첫 `<link rel="canonical">`의 주소(호스트 규칙에만 쓴다), 수집의 `readProductPage`가 읽는 메타 키 일곱 개(`og:title`·`twitter:title`·`og:image`·`product:price:amount`·`product:price:currency`·`og:price:amount`·`og:price:currency`)의 키마다 첫 값, `Product`라는 글이 든 `application/ld+json` 블록이다. 메타 키는 읽기처럼 `property`가 있으면 그것을, 없으면 `name`을 앞뒤 공백 없이 소문자로 본다. 읽기는 블록 어디에서든(`@graph` 포함) 상품을 찾으므로 블록은 통째로 보낸다. 스크립트 글은 형식이 ld+json인 것만 읽는다. `og:type`·`og:url`·`og:description`·`twitter:card`·`itemprop` 메타, 상품이 없는 블록(BreadcrumbList·Organization 등), 본문 글, 다른 스크립트, 쿠키, 저장소, 네트워크에는 닿지 않는다.
  - 칸마다 한도가 있다. 주소 4,096자(넘으면 통째로 빈 값, 자른 주소는 다른 페이지를 가리키므로), 제목 1,000자(대리 문자 쌍을 깨지 않고 자름), 메타 일곱 개(값 4,096자에서 자름), JSON-LD 16개(65,536자 넘는 블록은 통째로 버림)다. 전체는 UTF-8 JSON으로 64KiB 이하다. 상품 블록, 메타 순서로 들어가는 것만 넣는다. 스크립트의 키 목록과 한도는 서버 상수(`PAGE_SNAPSHOT_META_KEYS`·`PAGE_SNAPSHOT_LIMITS`)에서 글로 만든다.
  - 결과는 `completion(JSON 글)` 한 번이다. 예상과 다른 문서여도 빈 요약으로 끝나 단축어가 멈추지 않는다. ASCII만 쓴다.
- `POST /api/share/links`
  - 선택 칸 `page`를 받는다. 요약 객체나 그 JSON 글(단축어의 텍스트 칸)이다. `{ url }`만 보내는 이전 요청은 그대로다.
  - zod로 엄격하게 검사한다(`url`·`title`·`canonical`·`metas`·`jsonLd`, 메타 키는 위 일곱 개만, 칸마다 스크립트와 같은 한도, 전체 64KiB). 맞지 않으면 요약만 버리고 링크는 지금처럼 담는다(201·200). 새로 담았으면 메시지가 "담았어요. 다만 페이지 정보는 읽지 못했어요. 단축어에 moti의 스크립트를 다시 붙여 넣어 주세요."다. 이미 담긴 링크는 요약을 쓰지 않으므로 "이미 담아둔 상품이에요."그대로다. 응답 모양(`result`·`message`)은 같다. 400 `invalid_page`는 없앴다. 링크 검사가 먼저라 링크가 없으면 `invalid_link`이고, 한도를 넘는 본문은 413이다.
  - 본문 한도는 `page`가 있을 때만 8KiB + 2 × 64KiB = 136KiB(139,264바이트)다. JSON 글로 보낸 요약은 따옴표와 역슬래시가 한 번 더 이스케이프되어 최대 두 배가 된다. `page`가 없는 본문은 이전처럼 8KiB를 넘으면 413이다. 호스팅 한도 4.5MB보다 훨씬 작다. 키 형식만 맞으면 누구나 이 경로가 136KiB를 읽게 할 수 있다(이전에는 8KiB).
  - 응답의 모양은 바뀌지 않았다. 쓸 수 있는 요약이나 요약 없는 요청의 메시지도 그대로다.
- 서버의 요약 읽기(`share/infrastructure/shared-page-reader.ts`, 도메인 `share/domain/page-snapshot.ts`)
  - 공유한 링크의 호스트가 요약 주소(`url`)의 호스트나 요약의 대표 주소(`canonical`)의 호스트와 정확히 같아야 한다(http·https 무관, 하위·상위 도메인은 다름). 요약 주소는 http(s) 주소여야 한다(읽기의 기준 주소). 아니면 요약을 무시한다. Safari는 보고 있는 주소나 페이지의 대표 주소를 공유하므로, 모바일 페이지(`m.`)를 www 대표 주소로 공유해도 쓴다. 대표 주소는 같은 요약에서 오므로 보내는 쪽이 `url`로 이미 주장할 수 있는 것 이상을 더하지 않는다. 대표 주소는 이 규칙에만 쓰고 읽기에는 쓰지 않는다.
  - 요약을 최소 HTML로 다시 만든다. 제목·속성 값은 `& < > " '`를 모두 엔티티로 바꾸고, JSON-LD 안의 `<`는 `<`로 바꾼다. 받은 값은 요소를 열거나 닫거나 더할 수 없다.
  - 그 문서를 수집과 같은 `readProductPage`가 요약의 주소에서 읽고 `decideOutcome`(`pickSinglePrice` 포함)이 이름·하나뿐인 가격·사진 주소를 정한다. 이름 규칙과 가격 규칙이 서버 수집과 같다. 고정 페이지 9개에서 요약해 읽은 결과가 서버가 그 페이지를 읽은 결과와 같다는 것을 단위 검사가 확인한다.
  - 이름이 없으면(상품 정보 없음) 요약은 쓸모가 없고 지금처럼 담는다. 서버 수집과 공유 글의 이름이 그대로 쓰인다. 요약을 읽다 예외가 나도 링크는 담는다.
- 저장(마이그레이션 `20261122000000_share_page.sql`)
  - 읽은 결과는 새 상품의 첫 수집 작업 열 넷(`metadata_jobs.shared_title`·`shared_amount_minor`·`shared_currency`·`shared_image_url`)에 둔다. 검사는 수집 결과와 같다(`is_clean_title`, 금액 1~2^53−1, 통화 대문자 세 글자, `is_web_url` 4096자, 금액과 통화는 함께). 대기·실행 중인 작업만 가질 수 있다.
  - 읽은 이름은 상품의 수집 전 이름(`products.title`)이 된다. 공유 글의 이름보다 앞선다. 화면은 담은 바로 뒤부터 이 이름을 보인다.
  - `moti.add_link`와 `public.moti_share_add`에 기본값 null인 인자 넷(`p_shared_title`, `p_shared_amount_minor`, `p_shared_currency`, `p_shared_image_url`)을 더했다. 이번 요청이 새로 더한 상품에만 쓴다. 이미 담긴 상품(`duplicate`)은 상품도 작업도 그대로다. 검사를 지나지 못하는 값은 읽은 결과만 버리고 링크는 담는다. 이전 앱의 여섯 인자 호출과 `moti_save_link`의 다섯 인자 호출은 뜻이 같다. 마이그레이션을 배포보다 먼저 적용해도 된다. 어댑터는 읽은 결과가 있을 때만 새 인자를 보낸다.
  - `moti_share`는 이 네 열의 INSERT만 더 받았다. 소유(`moti_share`), `revoke`·`grant`, 보안 정의자, `search_path=''`, 익명만 실행하는 규칙은 4c의 틀 그대로다.
  - 작업이 끝나면(성공, 실패, 대체, 시도 소진) 트리거 `metadata_jobs_forget_shared_page`가 네 열을 지운다. 어떤 역할·함수가 끝내든 같다. 임대가 끝나 같은 세대에서 다시 맡거나 멈춤에서 다시 시작하면 그대로 남는다. "다시 가져오기"의 새 세대 작업에는 없다.
  - `moti_metadata_claim`의 작업에 `shared_page`(없으면 null)를 싣는다.
  - 예약 작업자(`moti_worker_next`)는 읽은 결과가 있는 작업을 고르지 않는다. 작업자는 사진을 복사할 수 없고 막힌 쇼핑몰은 읽기도 실패하기 때문이다. `moti_worker`는 `shared_title` 열 SELECT 하나만 더 받았다.
  - 그래서 깨우기(`moti.metadata_wake`)가 한 번도 시작하지 않은 대기 작업에 더해, 읽은 결과가 있고 멈췄으며(`moti.is_stalled`: 임대가 끝났거나 60초 넘게 대기) 시도가 남은(`attempts < 3`, 맡기의 한도) 작업도 돌려준다. 다음 수집이 같은 세대의 작업을 다시 맡아 읽은 결과로 끝낸다. 시도를 다 쓴 작업과 임대가 남은 작업, 읽은 결과가 없는 멈춘 작업(예약 작업자의 몫)은 전처럼 돌려주지 않는다.
- 수집 실행기(`metadata/application/collection.ts`)
  - 맡은 작업에 읽은 결과가 있으면 쇼핑몰 페이지를 읽지 않고 그 결과로 끝낸다. 사진은 지금처럼 서버가 안전한 사진 경로(SSRF 차단, 바이트 판별, sharp → WebP, 비공개 Storage)로 가져온다. Referer의 페이지는 공유한 링크다.
  - 키로 담은 상품은 지금처럼 소유자가 moti를 열 때 깨우기로 수집한다.
- "공유 저장" 안내(`share-view.ts`, `ShareView.tsx`)
  - 첫 단축어의 다섯 단계는 그대로다.
  - 아래에 "Safari에서 상품 정보까지 담기 (선택)"이 생겼다. 왜 필요한지(네이버·쿠팡·G마켓)와 다섯 단계를 적었다. 첫 단축어 복제(받을 항목은 Safari 웹 페이지만, 복제본에 남은 "입력이 없는 경우: 클립보드 가져오기"는 "중단"으로 바꿔 JavaScript 단계가 글을 받지 않게), 설정 → 앱 → 단축어 → 고급의 "스크립트 실행 허용"(이전 iOS는 설정 → 단축어 → 고급), "웹 페이지에서 JavaScript 실행"(대상 단축어 입력, 예시 스크립트 지우고 붙여 넣기), JSON 본문에 텍스트 키 `page` = "JavaScript 결과", Safari에서 "moti에 담기 (Safari)"로 공유(사이트마다 처음 실행할 때 묻는 "허용")다.
  - 스크립트 글, "스크립트 복사", "아직 실제 iPhone에서 확인하지 않았어요."와 가격을 다시 확인하지 못한다는 안내가 있다. 흰색·중립 회색·차콜만 쓴다.
- `docs/api/openapi.json`을 다시 생성했다. 요청에 `page`가, 201 설명에 페이지 정보를 읽지 못했다는 메시지가, 413 설명에 136KiB 한도가 들어갔다. 400에는 `invalid_link`만 남았다.

## 설계 선택

- 동기 적용과 저장 후 적용을 비교했다.
  - 공유 요청에서 바로 적용하려면 키(익명, `moti_share`)가 상품의 수집 열·가격 열을 쓰고 사진을 Storage에 올려야 한다. Storage는 소유자 JWT만 받는다. 키의 힘이 크게 넓어진다.
  - 그래서 읽기와 결정만 공유 요청에서 하고, 결과는 첫 작업에 맡겨 다음 수집이 쓰게 했다. 작업의 임대·세대·시도, 사진 사본 이름, `metadata_complete`의 검사를 그대로 쓴다.
- 받은 요약 전체(최대 64KiB)가 아니라 읽은 결과(이름·금액·통화·사진 주소)만 저장한다. 저장 크기는 열 검사로 이미 묶인다(이름 120자, 주소 4,096자). 요약 자체는 DB에 남지 않는다.
- 요약은 별도 표가 아니라 작업 열에 둔다. 작업과 수명이 같고, 끝날 때 트리거 하나로 지운다. 새 함수 권한은 필요 없다(트리거는 쓰는 행만 바꾼다).
- 신뢰 규칙. 저장 키는 추가 전용이고, 유출된 키는 가짜 요약을 보낼 수 있다.
  - 요약은 이번 요청이 새로 더한 상품에만 쓰고 이미 담긴 상품은 바꾸지 않는다.
  - 공유한 링크의 호스트는 요약 주소나 대표 주소의 호스트와 같아야 한다. 하위 도메인도 다르게 본다. Safari는 보고 있는 주소나 대표 주소를 공유한다.
  - 값은 수집 결과와 같은 검사를 지난다. 사진은 받은 바이트가 아니라 주소뿐이고, 서버가 같은 안전한 경로로 가져온다.
  - 키 없이도 아무 링크(자기 사이트의 og 정보 포함)를 담을 수 있었으므로, 이 규칙 아래 요약이 더하는 힘은 "같은 호스트의 새 상품에 다른 이름·가격·사진 주소를 붙이는 것"뿐이다. 한 시간 30번 한도와 키 폐기는 그대로다.
- `page`를 JSON 글로도 받는다. 단축어의 JSON 본문 칸에 변수를 넣기 가장 확실한 형태가 텍스트이기 때문이다. 기기에서 확인하지 않아 객체도 받는다.
- 두 번째 단축어로 나눴다. "웹 페이지에서 JavaScript 실행"은 Safari 웹 페이지만 받고 다른 입력이면 단축어가 멈춘다. 쇼핑 앱의 글이나 클립보드를 받는 첫 단축어에 넣으면 그 경로가 깨진다.
- 스크립트를 화면이 보이는 글과 같은 TS 상수 하나로 두었다. 단위 검사가 같은 글을 실행한다. 저장소에 jsdom·happy-dom이 없어 `tests/support/page-snapshot-dom.ts`의 작은 DOM 대역(htmlparser2 트리 위의 `getElementsByTagName`·`getAttribute`·`textContent`·`title`·`location.href`)으로 실행한다.

## 검증

| 검사 | 결과 |
| --- | --- |
| 단위 (`npm test`) | 1,564개 통과 (main 1,488개) |
| 실제 DB | persistence 330개, service 66개 통과 (main 308·64개) |
| 실제 HTTP | 56개 통과 (main 54개) |
| 실제 스택 브라우저 (PC Chromium, iPhone 크기 WebKit) | 60개 통과 (main 58개) |
| Supabase 없는 브라우저 (`tests/ui`) | 50개 통과 (main 50개) |

- 단위: 스크립트(고정 상품 페이지의 요약 모양, 세션 값·토큰 메타·본문 제외, 칸·전체 한도와 상품 블록 우선, 빈 페이지, 오류에도 끝내기, 쿠키·네트워크 없음), HTML 다시 만들기의 이스케이프, 호스트 규칙, 요약 읽기가 수집과 같은 결과, 명령, 서비스(이름 우선, 쓸 수 없는 요약, 예외, 이전 단축어), 처리기(Given–When–Then: 객체·JSON 글, 두 번 이스케이프된 64KiB 근처, `invalid_page` 열네 가지, 링크 우선, 413 두 가지), 실행기(쇼핑몰을 읽지 않고 끝냄), 안내 문구, API 문서.
- 실제 DB: 첫 작업의 네 열과 상품 이름, `duplicate`의 무변경, 버리는 값 아홉 가지, 이름만 있는 결과, 맡을 때 받고 끝낼 때 지움(성공·실패·다시 가져오기), 임대가 끝나 다시 맡으면 남음, 예약 작업자가 고르지 않음, 이전 앱 호출, 어댑터 왕복, 열 권한, `moti_share`·`moti_worker`의 권한 목록과 함수 서명.
- service: 쇼핑몰이 막는 상황(실제 DB·Storage·sharp, 쇼핑몰만 대역)에서 스크립트가 고정 페이지에서 만든 요약으로 담고, 깨우면 쇼핑몰을 읽지 않고 이름·가격과 사진 사본(`copied`)을 남긴다. 다른 호스트의 요약과 이미 담긴 링크의 요약은 쓰지 않는다.
- 실제 HTTP: 루프백 링크(운영 가져오기 정책이 거절)에 스크립트 결과를 `page`로 보내면 201이고 이름이 바로 보이며, 깨운 뒤 이름·가격이 채워지고 사진은 같은 정책으로 `blocked_address`다. 형식이 다른 `page`는 400, 한도를 넘는 본문은 413이고 아무것도 담지 않는다.
- 실제 스택 브라우저(두 기기): Safari 안내와 스크립트 글이 상수와 같고 복사 상태가 보이며 중립 색이다. 스크립트 결과로 담은 상품은 다시 열면 이름과 12,900원을 보이고 "정보를 가져오지 못했어요"가 아니다. 기존 접근성 검사가 새 영역을 포함한 화면에서 통과한다.

`main`(924663d)에서 시작한 `feat/share-page`에 리뷰 반영을 더한 상태(f32af9a 위)의 로컬 `npm run verify`(종료 0)로 개수를 확인했다. 첫 커밋(f32af9a)의 개수는 단위 1,551, persistence 328이었다.

- 리뷰 반영으로 더한 것: 형식이 다른 `page`의 201·메시지(처리기 열여섯 가지와 duplicate, 실제 HTTP), 보내는 메타 일곱 키·키마다 첫 값·property 우선, 상품 블록만, ld+json 형식 확인 뒤에만 글 읽기(스크립트), canonical 호스트 규칙(m.↔www 허용, 다른 사이트 거절), 멈춘 읽은 결과 작업을 깨우기가 다시 꺼내 읽은 결과로 끝내는 것과 꺼내지 않는 세 경우(실제 DB), 안내 문구(단위·두 기기 브라우저).

## 남은 범위

- 실제 iPhone에서 확인하지 않았다. 단축어 앱의 동작 이름("웹 페이지에서 JavaScript 실행", "스크립트 실행 허용", "JavaScript 결과"), 설정 경로(iOS 18의 설정 → 앱 → 단축어 → 고급), 복제, 받을 항목을 Safari 웹 페이지만 남기기, "입력이 없는 경우"의 "중단", 사이트마다 처음 묻는 "허용", JSON 본문의 텍스트 칸에 결과를 넣는 방법, 실행 시간 제한을 모두 기기에서 봐야 한다. 테스트의 페이지는 공개 상품 페이지를 본뜬 고정 페이지다.
- 실제 쇼핑몰 페이지는 PC Chrome(2026-11-17)에서만 봤다. 스크립트가 보는 것과 같은 머리 정보를 수집의 읽기로 읽었다.
  - 쿠팡: JSON-LD `Product`에서 이름, 1,257,120 KRW, coupangcdn 사진 주소를 얻었다. 그 사진 서버는 서버 요청에 200으로 답했다.
  - G마켓: 이름과 사진만 얻었다. 가격은 `og:description` 글 안에만 있어 읽지 않는다(의도한 동작, 설명 글에서 가격을 뽑지 않는다). 담은 뒤 가격은 비어 있다.
  - 네이버 스마트스토어는 보지 않았다. iPhone Safari의 모바일 페이지(`m.` 호스트 등)는 PC와 다른 머리 정보를 둘 수 있다.
- 단축어의 JSON 본문이 `page` 글을 어떻게 이스케이프하는지 기기에서 확인하지 않았다. 136KiB 한도는 따옴표·역슬래시만 두 배가 된다는 가정이다. 단축어가 한글 등 ASCII 밖의 글자를 `\uXXXX`로 바꾸면 한 글자(UTF-8 3바이트)가 6바이트가 되어 두 배를 넘을 수 있다. 그러면 큰 요약을 보낸 요청은 413이 되고 링크도 담기지 않는다.
- 이 쇼핑몰의 가격 다시 확인(매일 가격 확인, 다시 가져오기)은 여전히 서버가 페이지를 읽으므로 실패한다. "다시 가져오기"를 누르면 새 세대가 쇼핑몰을 읽어 실패 상태가 된다(이름·가격·사진은 남는다). 다시 공유해도 이미 담긴 상품은 바꾸지 않는다.
- 사진 서버도 막으면 사진은 실패로 남는다(이름·가격은 남는다). 쇼핑몰 사진 서버의 실제 응답은 확인하지 않았다.
- 한 블록이 64KiB를 넘는 JSON-LD(후기가 많이 든 상품 등)는 통째로 빠진다. 그때는 og 메타만 남아 가격이 없을 수 있다.
- 호스트 규칙이 정확히 같은 호스트라, Safari가 공유한 주소의 호스트가 페이지의 `location.href`와 대표 주소 어느 쪽과도 다르면(대표 주소가 없는 페이지의 클라이언트 쪽 이동 등) 요약을 쓰지 않는다.
- 유출된 키는 같은 호스트의 새 상품에 꾸민 이름·가격·사진 주소를 붙일 수 있다. 사진은 서버가 같은 보호 아래 가져온다. 키를 폐기하고 상품을 지우면 된다.
- 상품이 있는지는 블록 글에 `Product`가 있는지로 고른다. `\u0050roduct`처럼 이스케이프로만 적은 블록은 빠진다(읽기는 찾았을 것이다).
- 형식이 다른 `page`는 요약만 버리므로, 오래되거나 고친 스크립트로 공유해도 링크는 담기고 메시지로만 알린다.
- 단축어 경로가 키 형식만 확인하고 읽는 본문이 8KiB에서 136KiB로 커졌다. 요약은 DB가 키를 확인하기 전에 처리된다. 읽은 결과를 담기와 한 번의 RPC로 보내기 때문에, 처리기의 JSON 파싱·zod 검사와 서비스의 HTML 다시 만들기·`readProductPage` 읽기가 모두 키 확인보다 먼저다. 형식만 맞는 가짜 키로도 요청마다 64KiB 이하의 요약 하나를 이렇게 처리하게 할 수 있다(그 뒤 DB가 401로 거절한다). IP별 제한은 호스팅에 맡긴다.
- 운영 마이그레이션 적용, 배포, 실제 Google OAuth, 호스팅 설정은 검증하지 않았다. 배포는 별도 승인이다.
