# 공유한 글에서 링크와 이름 읽기

iPhone 단축어 "moti에 담기"가 링크 대신 글을 넘겨도 담기는 단위다. 쇼핑 앱이 공유 메뉴로 넘기는 값이 앱마다 다르다. 이전에는 `POST /api/share/links`가 `url` 칸이 링크 하나일 때만 담았다. 이번 단위는 글에 든 첫 링크를 담고, 그 위 줄을 수집 전 상품 이름으로 둔다. 앱 공유 링크의 추적 query도 같은 상품 판별에서 뺀다. "공유 저장" 화면의 안내는 실제 iPhone에서 동작한 구성으로 바꿨다.

## 왜

2026-11-15에 소유자가 실제 iPhone에서 운영 배포로 시험했다. 단축어가 받은 값은 다음과 같았다.

| 출처 | 단축어가 받은 값 | 이전 결과 |
| --- | --- | --- |
| Safari | 페이지 주소 `https://www.musinsa.com/products/7023777` | 담김 |
| 무신사 앱 | 짧은 링크 `https://musinsa.onelink.me/PvkC/rez5hvvc`. 301로 `https://www.musinsa.com/products/5016455?af_referrer_customer_id=…&source_caller=sdk&af_force_deeplink=true&shortlink=rez5hvvc&af_dp=…&is_retargeting=true&af_channel=mobile_share&pid=af_app_invites&af_referrer_uid=…&onelink_id=PvkC&af_siteid=…`로 넘어간다(값은 줄였다) | 담김. 수집이 리디렉션을 따라가 성공했다 |
| 쿠팡 앱 | 글 `"쿠팡을 추천합니다!\n로투스 벨기에 와플 초코\nhttps://link.coupang.com/a/iGa1zKNs4a"` | 400 `invalid_link`("상품 링크를 찾지 못했어요") |
| 네이버 스마트스토어 | `https://m.smartstore.naver.com/whatkey/products/13459235684?nl-query=…&nl-au=…` | 네이버 앱의 공유 메뉴에는 단축어가 없다(자체 공유와 "링크 복사"뿐) |

- 쿠팡은 페이지 읽기를 막는다(`blocked_by_site`). 그래서 공유한 글의 상품 이름이 moti가 얻을 수 있는 유일한 이름이다.
- 단축어의 "입력에서 URL 가져오기 → 목록에서 항목 가져오기"는 기기에서 빈 값을 보냈다. "단축어 입력"을 그대로 보내면 동작했다. 그래서 링크 찾기를 단축어가 아니라 서버가 한다.
- 네이버 앱에서는 링크를 복사한 뒤 단축어를 실행한다. 단축어는 입력이 없으면 클립보드를 보낸다.

## 바뀐 동작

- `POST /api/share/links`의 요청 본문은 그대로 `{ "url": string }`이다. 이미 만든 단축어도 그대로 동작한다. `url`에는 링크나 링크가 든 글을 넣을 수 있다.
  - 서버는 글에서 첫 `http://`·`https://` 링크를 찾는다(대소문자 무시). 링크는 공백, `<>"`, 둥근 따옴표, 전각 문장 부호·괄호 `，。！？（）【】〈〉《》「」『』、`, 한글 음절·자모에서 끝난다. 날 한글은 공유 링크에 들어가지 않는다(앱은 한글 경로를 퍼센트 인코딩해 보낸다). 그래서 "…/p/1입니다"는 "…/p/1"이다. 끝의 `.,!?;:'`과 링크가 열지 않은 닫는 괄호는 뗀다. 괄호 수는 한 번 세고 뗄 때마다 줄이므로 시간은 링크 길이에 비례한다.
  - 찾은 링크는 이전과 같은 `parseLink(link, "")`를 지난다. 4096자, 제어 문자, 계정 정보, http(s)만 허용하는 규칙이 그대로다. 사설 주소 차단은 수집 단계에 그대로 있다.
  - 링크가 없는 글, 빈 값, 짝이 없는 대리 문자가 든 글, 5,000자(code point)를 넘는 글은 이전처럼 400 `invalid_link`다.
  - 한도는 둘이고 먼저 닿는 쪽이 적용된다. `url`은 5,000자(code point) 이하(넘으면 400), 요청 본문 전체는 UTF-8로 8KiB(8,192바이트) 이하(넘으면 413 `payload_too_large`)다. 한글은 한 글자가 3바이트라 한글 글은 약 2,700자에서 413이 먼저 난다. 5,000자 한도는 ASCII에 가까운 글에서만 닿는다. OpenAPI 설명도 두 한도를 함께 적는다.
  - 응답의 모양과 `message`는 바뀌지 않았다.
- 이름은 링크 앞의 가장 가까운, 무언가를 이름하는 글이다. 링크와 같은 줄의 앞부분을 먼저 보고, 쓸 수 없으면 그 위 줄로 올라간다. 링크 바로 앞의 여는 괄호(`([{（【〈《「『`)는 뗀다. 그 뒤 글자나 숫자(`\p{L}`·`\p{N}`)가 없거나 쌍점(`:`·`：`)으로 끝나는 글은 건너뛴다. 그래서 "상품명\n▶ https://…"와 "상품명\n링크: https://…"는 "상품명"이고, "（https://…）"는 이름이 없다. 이 규칙은 같은 줄의 앞부분과 위 줄에 똑같이 쓴다. 쿠팡의 예에서는 "로투스 벨기에 와플 초코"다. 첫 링크보다 위의 줄에는 링크가 없으므로 "링크인 줄"을 따로 거를 필요가 없다. 링크 뒤의 글은 쓰지 않는다. 제어 문자는 공백으로 바꾸고 공백을 하나로 줄인 뒤 앞뒤를 자르고 NFC로 맞춘다. 120자(code point)에서 자르고 끝 공백을 다시 뗀다.
- 이름은 `products.title`(수집한 이름 열)에 처음 값으로 들어간다. 새 열은 없다.
  - 화면은 이전처럼 `coalesce(owner_title, title)`을 보인다. 그래서 수집 전에는 "새로 담은 상품" 대신 이 이름이 보인다.
  - 수집이 성공하면 수집한 이름이 `title`을 덮는다. 소유자 저장, 예약 실행, 가격 확인 모두 마찬가지다. 수집이 실패하면 이름이 남는다.
  - 소유자가 고친 이름(`owner_title`)은 그 뒤 수집보다 계속 앞선다.
  - 이미 담긴 링크에는 이름을 쓰지 않는다(`duplicate`).
  - 백업은 `title`을 `collectedTitle`로 이미 담는다. 그래서 형식 v1이 바뀌지 않고 그대로 왕복한다.
- 마이그레이션 `20261121000000_share_text.sql`
  - `moti.add_link`에 `p_title text default null`을 더했다. `moti_save_link`의 다섯 인자 호출은 고치지 않았고 뜻도 같다.
  - `moti.is_clean_title`을 지나지 못하는 이름(null, 빈 값, 앞뒤 공백, 121자 이상, 제어 문자, NFC 아님)은 열의 기본값 "새로 담은 상품"으로 바꾼다. 이름은 힌트일 뿐이므로 이름 때문에 링크를 잃지 않게 했다.
  - `public.moti_share_add`도 `p_title text default null`을 받는다. 이 인자를 보내지 않는 이전 앱의 호출도 그대로 담긴다. 마이그레이션을 배포보다 먼저 적용해도 된다.
  - 전용 역할 `moti_share`는 `products.title` 열의 INSERT 권한 하나를 더 받았다. 소유, `revoke`·`grant`, 익명만 실행하는 규칙은 4c의 틀 그대로다. catalog 검사가 권한 목록과 함수 서명을 고정한다.
- 같은 상품 판별(`parseLink`의 `identityUrl`)에서 빼는 query가 늘었다.
  - 이전부터 빼던 것: `utm_*`, `gclid`, `fbclid`, `msclkid`
  - 더한 것: `af_*`, `is_retargeting`, `shortlink`, `source_caller`, `onelink_id`, `nl-query`, `nl-au`
  - 이름은 대소문자를 무시한다. `pid`는 `af_*`와 함께 올 때만 뺀다. 혼자 오는 `pid`는 상품 번호로 쓰는 쇼핑몰이 있어서 남긴다.
  - 원문 링크(`sourceUrl`)는 바꾸지 않는다. 판별은 `parseLink` 한 곳에서 하므로 화면 저장(`POST /api/links`), 단축어(`POST /api/share/links`), 목업, 화면의 복원 미리보기, 복원이 모두 같은 규칙을 쓴다. DB는 판별 주소를 다시 계산하지 않는다(`identity_hash`는 받은 판별 주소의 해시다).
- "공유 저장" 안내(`share-view.ts`의 `shortcutSteps`, `shareWithoutShortcuts`)
  1. 세부 사항(ⓘ)에서 "공유 시트에서 보기"를 켜고, 편집기 맨 위의 입력 받기 블록("공유 시트에서 … 받기")에서 받을 항목을 URL, Safari 웹 페이지, 텍스트로 고른다
  2. 같은 맨 위 블록의 "입력이 없는 경우: 계속하기"에서 "계속하기"를 "클립보드 가져오기"로 바꾼다. iOS는 받을 항목과 "입력이 없는 경우"를 ⓘ 세부 사항이 아니라 이 블록에 둔다
  3. "URL 콘텐츠 가져오기" 하나: POST, 헤더 Authorization, JSON 본문의 `url` = "단축어 입력". "입력에서 URL 가져오기"는 넣지 않는다고 적었다.
  4. "사전 값 가져오기"로 `message`를 꺼내 "알림 보기"
  5. 저장 키 붙여 넣기
  - 2단계에 "공유 메뉴에 단축어가 없는 앱(예: 네이버 앱)에서는 링크를 복사한 뒤 홈 화면이나 위젯에서 ‘moti에 담기’를 실행해요."를 더했다.
  - 1단계의 소개 문장은 실제 iPhone에서 확인한 구성이라고 바꿨다.
  - 색은 이전 그대로 흰색·중립 회색·차콜이다.
- `docs/api/openapi.json`을 다시 생성했다. 단축어 경로의 설명과 400 설명이 바뀌었다.

## 설계 선택

- 이름을 둘 곳으로 세 가지를 비교했다.
  - `title`에 처음 값으로 넣기(선택)
  - 새 열 `shared_title`
  - `owner_title`에 넣기
- `title`은 "수집 전 이름"이 필요로 하는 동작을 이미 한다. 수집 성공은 덮고, 실패는 남기고, 소유자 이름은 앞선다. 백업도 이미 담는다. 새 열을 두면 `product_json`, 백업 형식, 복원, 작업자 권한을 모두 고쳐야 한다. `owner_title`에 넣으면 수집한 이름이 영영 가려진다.
- 대가도 있다. 수집이 실패한 상품은 공유한 글의 이름을 "수집한 이름"으로 백업에 내보낸다. 수집이 늘 막히는 쿠팡에서는 그게 바라는 결과다.
- 이름 검사가 실패하면 링크를 거절하지 않고 기본 이름으로 담는다. 서버의 `readSharedText`가 이미 `is_clean_title`에 맞는 값만 만든다. 그러니 이 대체는 PostgREST를 직접 부르는 호출에만 일어난다.
- 링크 찾기는 서버의 도메인 함수 `src/features/share/domain/shared-text.ts`에 있다. 단축어 쪽 동작은 기기에서 빈 값을 보냈다. 서버에 두면 이미 설치한 단축어도 고칠 필요가 없다.

`main`(2e55658)에서 시작한 `feat/share-text`의 로컬 `npm run verify`(종료 0)로 개수를 확인했다. 리뷰 반영(전각 문장 부호·한글에서 링크 끝내기, 쓸모없는 이름 건너뛰기, 괄호 세기의 선형화, 두 한도 문서화, 맨 위 입력 받기 블록 안내) 뒤 b8d24d8 위에서 다시 실행한 `npm run verify`(종료 0)의 개수가 위 표다. 리뷰 반영의 Red는 `docs/evidence/share-text/red-review.txt`에 있다(단위 15개 실패, 괄호 4,980개 링크 144.9ms → 0.5ms).

- 단위: 쿠팡 글, Safari·무신사 짧은 링크, 같은 줄의 이름, 한글·전각 문장 부호·전각 괄호에서 끝나는 링크와 퍼센트 인코딩한 한글 경로, 기호만 있거나 쌍점으로 끝나는 글 건너뛰기, 닫는 괄호 4,980개, 빈 줄 건너뛰기, 링크 뒤의 글, 끝 문장 부호·괄호, 제어 문자·공백·NFC, 120자 자르기, 5,000자 경계, 거절되는 글 여섯 가지를 확인한다. 무신사 리디렉션 모양(만든 값)과 스마트스토어 query의 판별, 혼자 오는 `pid` 보존, 비슷한 이름의 query 보존, 화면 저장의 중복 판별도 확인한다. 명령과 처리기(Given–When–Then)는 쿠팡 글의 201과 저장소에 넘기는 이름, 링크 없는 글과 빈 값의 400을 확인한다. 안내 문구도 확인한다.
- 실제 DB:
  - 받은 이름이 `title`에 들어가고, 수집 성공이 덮는다.
  - 수집이 실패해도 이름이 남고, 소유자 이름은 그 뒤 수집보다 앞선다.
  - 이름 여섯 가지는 기본 이름으로 담긴다.
  - 이미 담긴 상품의 이름은 바뀌지 않는다.
  - `p_title` 없이 부르는 이전 호출도 담긴다.
  - 백업에 나가고 복원 뒤에도 남는다.
  - 어댑터가 이름을 넘긴다.
  - `moti_share`의 권한 목록과 함수 서명이 고정돼 있다.
- service: AppsFlyer query가 붙은 쇼핑 앱 글로 담는다. 이어서 같은 상품의 맨 주소가 `duplicate`인지, 실제 수집 실행기가 고정 페이지의 이름으로 바꾸는지 확인한다.
- 실제 HTTP: 쿠팡 글을 `url` 칸에 그대로 보내면 201이고, 보관함에 글 속 링크와 이름으로 보인다. 링크 없는 글은 400이고 아무것도 담지 않는다.
- 실제 스택 브라우저(두 기기): 안내가 새 구성(클립보드, 단축어 입력, 단축어 없는 앱)을 보이고 "목록에서 항목 가져오기"가 없다. 루프백 링크가 든 글로 담은 상품은 깨우기 뒤 수집에 실패한다. 그래도 카드가 글 속 이름으로 보인다.

Red는 `docs/evidence/share-text/red.txt`에 있다.

- 단위: 같은 서명의 동작 없는 대역(`readSharedText`가 null, 안내가 빈 값)과 이전 판별 규칙으로 22개가 실패했다.
- 실제 DB: 마이그레이션이 없을 때 persistence 13개와 service 1개가 실패했다(PGRST202, 권한 목록, 서명). `p_title` 없이 부르는 이전 호출 검사는 처음부터 통과하는 보호 검사다.
- 실제 스택 브라우저: 서버 쪽을 구현하고 안내를 바꾸기 전 빌드에서, 안내 검사가 두 기기에서 실패했다.
- 안내를 바꾼 뒤 첫 `npm run verify`에서 같은 브라우저 검사가 두 기기에서 다시 실패했다. 이번에는 검사의 잘못이었다. 실제 화면 카드의 이름은 "이름, 쇼핑몰 상세 보기"인데 검사가 "이름 상세 보기"를 찾았다. 검사를 고친 뒤 전체 검사가 통과했다.
- 실제 HTTP의 Red는 따로 보지 못했다. 마이그레이션이 없을 때는 persistence 실패에서 실행기가 멈추고, 마이그레이션을 넣은 뒤에는 서버 구현이 함께 들어갔기 때문이다.

## 남은 범위

- 실제 iPhone에서 새 서버와 새 안내로 쿠팡 앱 글, 네이버 앱의 클립보드 경로, 받을 항목에 "텍스트"를 더한 구성을 다시 시험하지 않았다. 위 관찰은 이 변경 전의 운영 배포에서 한 것이다. 운영 마이그레이션 적용과 배포는 별도 승인이다.
- 이 변경 전에 담긴 상품은 이전 판별 주소를 그대로 가진다. 예를 들어 `af_*`가 붙은 채 담긴 무신사 상품을 Safari 주소로 다시 담으면 새 상품이 된다. 지울 상품은 상세의 "삭제"로 지운다.
- 복원은 파일의 링크에서 판별 주소를 새 규칙으로 다시 만든다. 그래서 이전 판별 주소를 가진 행은 복원에서 짝을 찾지 못한다. 그 행은 지워지고 새 행으로 들어가며, id·수집 상태·사진을 잃고 다시 수집한다. 또 추적 query만 다른 두 상품이 든 이전 백업 파일은 이제 새로 빼는 query(`af_*`, `nl-query` 등)만 달라도 "같은 링크가 두 번 있어요"로 거절된다. 이전에는 두 상품으로 복원됐다. 이전 판별 주소에 그런 query가 남은 행은 복원할 때 지워지고 다시 더해진다(id·수집 상태·사진을 잃는다). 운영 DB에는 지금 그런 행이 없다. 형식 v1 자체는 바뀌지 않았다.
- 짧은 링크(`musinsa.onelink.me/…`, `link.coupang.com/…`)는 리디렉션을 따라가지 않고 짧은 링크 그대로 판별한다. 같은 상품을 Safari 주소로 담은 것과 중복으로 알아보지 못한다. 공유할 때마다 짧은 링크가 바뀌면 같은 앱에서 다시 담아도 새 상품이다(share.md의 남은 범위와 같다).
- 이름 줄을 고르는 규칙은 관찰한 쿠팡 글 하나에 맞췄다. 다른 앱이 이름 아래에 링크를 두지 않거나 홍보 문구를 링크 바로 위에 두면 그 문구가 이름이 된다. 특히 다른 줄 없이 인사말 한 줄 바로 아래에 링크가 오면(예: "쿠팡을 추천합니다!\nhttps://…") 인사말이 이름이 된다. 글자가 있고 쌍점으로 끝나지 않으므로 건너뛰는 규칙에 걸리지 않는다. 소유자가 상세에서 고칠 수 있고, 수집이 성공하면 바뀐다.
- `pid`를 혼자 오면 남기는 규칙은 요청한 목록과 다르다. 판단 근거는 위 "바뀐 동작"에 있다.
- 원문 링크는 추적 query를 지우지 않고 그대로 저장한다. 무신사 앱이 넘기는 값은 짧은 링크라 추천인 값이 없다. 그러나 리디렉션 뒤의 주소를 복사해 담으면 그 추천인 값이 `source_url`에 남는다. 원문에서도 지울지는 결정하지 않았다.
