# 매일 가격 확인 (5b)

소유자가 moti를 열지 않아도 위시 상품의 가격이 매일 새로워지게 하는 단위다. 5a의 예약 실행(한국 시간 06:17·14:17·22:17)이 남은 수집을 마친 뒤, 수집이 끝난 위시 상품의 상품 페이지를 서울 날짜 하루 한 번 다시 읽는다. 페이지가 하나뿐인 가격을 저장한 가격과 같은 통화로 보이면 마지막 확인 가격과 그 시각을 바꾸고, 그렇지 않으면 이전 가격과 시각을 그대로 두고 이유를 남긴다. 구매완료 상품, 소유자가 고친 이름(`owner_title`)과 수집한 이름(`title`), 사진은 건드리지 않는다. 소유자는 "자동 확인"의 실행 기록에서 확인한 가격 수와 지킨 가격 수를 보고, 상품 상세에서 어느 날 무슨 이유로 이전 가격을 보여주는지 본다. 이전에는 이미 가져온 상품의 가격이 소유자가 "다시 가져오기"를 누르기 전까지 그대로였다.

5단위를 나눈 두 번째 PR이다. 열 때 남은 사진 정리(5c)는 다음 PR이다. 가격 알림과 가격 이력은 범위 밖이다.

## 바뀐 동작

- 마이그레이션 `20261118000000_price_check.sql` 하나에 이 단위의 SQL이 있다. 병합한 마이그레이션은 고치지 않았다.
  - 상품에 `price_checked_at`(가장 최근 확인 시각이자 진행 중인 확인의 울타리)과 `price_check_code`(가장 최근에 정산한 확인이 이전 가격을 지킨 이유, 확인했거나 정산 전이면 null)가 생겼다. 이유는 닫힌 목록 15개(가져오기 실패 11개, `no_product_data`, `no_single_price`, `other_currency`, `internal`)이고, 이유가 있으면 시각도 있어야 한다. 두 검사는 함수를 부르지 않는 인라인 검사라 상품을 넣는 역할(`moti_share` 등)에 새 권한이 필요 없다. `product_json`이 두 열을 함께 보낸다. 백업과 복원은 다른 서버 상태처럼 두 열을 다루지 않는다(링크가 같은 상품은 그대로, 새 상품은 null).
  - `moti_worker`의 권한이 가격 확인에 필요한 만큼 늘었다. 상품의 수집 단계·마지막 확인 시각·가격 확인 시각 읽기, 가격 확인 두 열 쓰기, 실행 행의 가격 셈 두 열 쓰기다. `owner_title`·메모·옵션·revision·구매 열·사진 사본 열, 컬렉션, 키, Storage, 다른 함수는 여전히 없다. catalog 검사가 정확한 목록을 고정한다.
  - `moti_worker_next`는 고를 수집이 없으면 가격 확인 하나를 고른다. 위시이고 수집이 끝났으며(`ready`) 서울 날짜로 오늘 확인하지도 가격을 얻지도 않은 상품 중 확인한 적 없는 것, 그다음 가장 오래전에 확인한 것, 그다음 오래 담은 것부터다. 다른 요청이 잠근 상품은 건너뛴다. 고르면 `price_checked_at`을 지금으로 옮기고 이유를 지우며, 답은 상품 id·그 시각·링크뿐이다.
  - 새 익명 RPC `public.moti_worker_price(p_key, p_run, p_lease, p_product, p_checked_at, p_amount_minor, p_currency, p_code)`는 `moti_worker`가 소유하고 같은 검사(`moti.worker_run_owner`)로 시작한다. 가격(1 ~ 2^53−1, 대문자 세 글자 통화)과 이유(15개 중 `other_currency`를 뺀 14개) 중 정확히 하나만 받고, 아니면 `M0002`다. 상품의 `price_checked_at`이 고른 시각과 같고 위시일 때만 쓰며, 아니면 아무것도 쓰지 않고 `stale`이다. 같은 통화이거나 저장한 가격이 없으면 마지막 확인 가격·통화·시각을 바꾸고 `prices_confirmed`를 올린다. 다른 통화는 `other_currency`, 이유는 그 코드로 남기고 이전 가격과 시각은 그대로이며 `prices_kept`와 `failures[이유]`를 올린다. 정산은 `price_checked_at`을 정산 시각으로 옮겨 한 확인이 두 번 정산되지 않는다. 이름 인자가 없고 이름·사진 열을 쓰지 않는다.
  - `moti_worker_complete`는 수집한 위시 상품을 오늘 확인한 것으로도 남긴다. 가격을 썼으면 이유 없음, 다른 통화면 `other_currency`, 하나의 가격이 없으면 `no_single_price`다. 같은 날 그 상품을 다시 고르지 않는다. 정산 사이에 구매완료로 옮긴 상품은 두 열도 그대로다.
- 앱
  - `src/features/worker/domain/price-check.ts`의 순수 함수 `decidePriceCheck`가 3a의 가격 규칙을 다시 적용한다. 상품 이름이 없는 페이지는 `no_product_data`, 서로 다른 가격이 하나면 그 가격, 여럿이거나 없으면 `no_single_price`다. 옵션은 소유자의 글이라 페이지에 물을 수 없으므로 옵션마다 가격이 다른 페이지는 이전 가격을 지킨다.
  - 실행의 줄이 고른 일이 가격 확인이면 같은 엄격한 가져오기(15초)로 페이지를 읽고 `decidePriceCheck`의 결과를 `price`로 정산한다. 가져오기 실패는 그 코드, 읽는 중 예외는 `internal`이다. 수집과 가격 확인은 한 실행에서 함께 60개까지이고 둘 다 `next`·페이지 하나·정산 하나라 예산은 그대로다. 최악은 5 + 20 + (5 + 15 + 5) + 5 = 55초다. 실행은 여전히 예외를 던지지 않는다.
  - 저장 어댑터는 고른 시각을 DB가 준 글자 그대로 돌려보낸다. 밀리초로 반올림하면 모든 정산이 `stale`이 된다.
  - 상품 도메인과 보관함 계약에 `priceCheck: { checkedAt, code } | null`이 생겼다. 실행 기록과 예약 실행 응답의 `failures`는 수집 실패와 가격을 지킨 이유를 함께 받는다. `docs/api/openapi.json`을 다시 생성했다.
- 화면
  - "자동 확인"의 최근 실행이 "수집 3 · 실패 1 · 가격 확인 12 (이전 가격 유지 2)"처럼 확인한 가격 수(확인 + 지킴)를 보이고, 지킨 가격이 있을 때만 괄호를 붙인다. 이유별 줄은 가격 이유도 함께 센다("1건 · 페이지에서 가격을 하나로 정하지 못했어요.", "1건 · 페이지의 가격이 저장한 가격과 다른 통화예요."). 머리말이 위시 상품의 가격을 하루 한 번 다시 확인한다고 말한다.
  - 위시 상품의 상세는 가장 최근 확인이 이유를 남겼고 그 확인이 마지막 확인 가격보다 나중이면 가격 아래에 "{서울 날짜}에 가격을 다시 확인하지 못해 이전 가격을 보여줘요. {이유}"를 중립 회색 글자와 정보 아이콘으로 보인다. 카드와 "마지막 확인 {날짜}"는 그대로 마지막으로 확인한 가격의 날짜다. 보여줄 이전 가격이 없거나 구매완료이거나 그 뒤 소유자의 수집이 새 가격을 썼으면 줄이 없다.
  - 화면이 다시 읽은 상품을 합칠 때 가격과 함께 가격 확인도 반영한다.
- 워크플로와 스크립트는 바꾸지 않았다. 공개 저장소라 로그에는 여전히 정해진 문구만 남고 가격 셈은 자동 확인에만 있다.

## 설계 선택

이 단위의 큰 선택은 5a와 함께 정했다(계약 `5-design.md`, 후보 A). 작업자가 같은 실행에서 가격을 확인하고, 하루 한 번은 서울 날짜로 세며, 오래 확인하지 않은 것부터, 하나뿐인 가격과 같은 통화만, 실패는 이전 가격 유지, 이름과 사진은 건드리지 않는다. 구현하며 정한 것은 아래와 같다.

| 기준 | 고른 것 | 다른 길 |
| --- | --- | --- |
| 정산 울타리 | 고를 때 옮긴 `price_checked_at`과 위시. 정산이 다시 옮긴다 | 별도 확인 토큰 열. 열이 하나 늘고 같은 일을 한다 |
| 고를 때의 이유 | 지운다. 끊긴 확인은 이유 없이 남는다 | 남긴다. 오늘 날짜에 어제의 이유를 붙여 말하게 된다 |
| 소유자의 수집(`moti_metadata_complete`) | 바꾸지 않는다 | 소유자의 수집도 오늘 확인으로 남긴다 |
| 이전 가격 줄의 판단 | 원자료(`priceCheck`)를 계약에 싣고 화면의 순수 함수가 판단 | 서버가 판단한 줄만 싣는다 |

소유자의 수집은 바꾸지 않았다. 고르기는 오늘 가격을 얻은 상품을 고르지 않으므로, 소유자의 수집이 가격을 쓰면 그날은 다시 확인하지 않는다. 가격을 쓰지 못한 수집(여러 가격, 다른 통화)만 같은 날 작업자가 한 번 더 읽고 같은 이유를 남긴다. 그 비용은 상품당 하루 한 번의 페이지 읽기다. 대신 사진 복사까지 하는 가장 큰 소유자 함수를 새 마이그레이션에서 다시 정의하지 않아도 된다.

### 설계와 다르게 구현한 것

- 정산이 `price_checked_at`을 정산 시각으로 옮긴다. 계약은 고른 시각만 울타리로 썼다. 그대로면 같은 확인을 두 번 정산할 때 셈이 두 번 오른다. 이제 두 번째는 `stale`이다.
- 고를 때 `price_check_code`를 지운다. 계약은 말하지 않았다. 끊긴 실행이 고른 확인은 다음 서울 날짜를 기다리는 동안 어제의 이유를 오늘 날짜로 보이지 않는다.
- `other_currency`도 `failures`에 센다. 계약은 이유만 셌다. 이제 `failures`의 합은 실패한 수집과 지킨 가격의 합이고, 자동 확인에서 지킨 가격마다 이유 줄이 있다.
- 상품 이름이 없는 페이지는 가격이 하나여도 `no_product_data`로 이전 가격을 지킨다. 3a의 수집 규칙(이름이 없으면 상품 정보 없음)과 같게 했다.
- 이전 가격 줄은 위시 상품이고 이전 가격이 있을 때만 보인다. 계약의 조건(이유가 있고 확인이 마지막 확인 가격보다 나중)에 두 조건을 더했다. 구매완료 상품은 더 확인하지 않고, 이전 가격이 없으면 보여줄 이전 가격이 없다.
- 작업자의 수집 중 구매완료로 옮긴 상품은 가격 확인 두 열도 쓰지 않는다. 계약은 말하지 않았다.
- `PageRead`의 실패 코드를 가져오기 코드 11개로 좁혔다. 안전한 가져오기가 실제로 내는 것만 타입에 남겨 가격 확인이 수집 전용 이유(`attempts_exhausted`)를 받지 않는다.
- 커밋은 열 개다. 기능 다섯(판단 `5699309`, SQL `8ef0403`, 실행과 어댑터 `78abcbf`, 계약 `4e40a6d`, 화면 `b826f3c`), 테스트 셋(service `d4c31a2`, 계약을 바꾼 뒤 service 기대를 고친 `010a96e`, 실제 HTTP `02094c5`), 시각 확인 뒤의 줄바꿈 수정 하나, 문서 하나다. 계약의 5b 항목을 계층마다 나눴다. `4e40a6d`의 화면은 가격 이유의 문구를 아직 몰라 `b826f3c`에서 채웠다.

- 단위는 가격 판단(하나의 가격, 같은 가격을 두 곳에 적음, 옵션마다 다른 가격, 같은 숫자의 다른 통화, 가격 없음, 읽을 수 없는 가격, 이름 없는 페이지), SQL의 두 이유 목록과 TypeScript 목록의 일치(마이그레이션을 읽음, 재시도 목록도 가장 최근 정의를 읽게 바꿈), 실행의 가격 분기(고른 확인 그대로 보내기, 네 가지 지킨 이유, 정산 중 키 거절·실행 잃음, 수집과 같은 60개 한도), 두 처리기의 계약(보관함의 `priceCheck`, 예약 실행 응답의 가격 이유), 화면(실행 줄, 다섯 이유의 이전 가격 줄과 서울 날짜, 줄이 없어야 하는 다섯 경우, 카드·상세 가격 그대로, 다시 읽은 상품 합치기)을 확인한다.
- persistence는 고르기(수집 먼저, 답의 모양, 서울 자정 앞뒤 1초로 오늘과 어제를 가름, 오늘 가격을 얻은 상품·구매완료·수집이 끝나지 않은 상품 제외, 확인한 적 없는 것과 오래된 확인부터, 잠긴 상품 건너뛰기), 정산(같은 통화, 첫 가격, 다른 통화, 이유별 셈, 고른 뒤 구매완료의 `stale`, 한 번만 정산, 잘못된 입력 아홉 가지의 `M0002`, 실행 중 폐기 `M0012`, 닫힌 실행 `M0013`), 이름·소유자 이름·revision·`updated_at`·수집 단계·사진 사본·Storage 객체가 그대로인지, 작업자의 수집이 남기는 오늘의 확인, 두 어댑터(고른 시각을 그대로 돌려보내 `applied`, 끝내기와 소유자 기록의 가격 셈), 보관함 읽기의 `priceCheck`, 작업 역할의 함수·권한·정책과 익명 실행 목록을 확인한다.
- service는 실제 DB와 고정 페이지(쇼핑몰만 바꿈)로 다음 날의 새 가격(이름·사진 그대로, 같은 날 다시 읽지 않음), 여러 가격·다른 통화·막힌 쇼핑몰의 이전 가격과 이유, 구매완료 상품을 읽지 않음을 확인한다.
- 실제 HTTP는 작업 키로 부른 실행이 루프백 링크의 수집 끝난 상품을 확인해 `blocked_address`로 이전 가격을 지키고, 보관함이 그 확인을 계약대로 보이며, 같은 날 두 번째 실행은 다시 확인하지 않고, 소유자의 실행 기록이 두 실행의 가격 셈을 보이는지 확인한다.
- 실제 스택 브라우저는 두 기기에서 Node `fetch`로 GitHub처럼 실행한 뒤 자동 확인의 "수집 0 · 실패 0 · 가격 확인 1 (이전 가격 유지 1)"과 이유 줄, 상세의 ₩9,000·마지막 확인 날짜·이전 가격 줄(오늘 서울 날짜와 이유), 줄의 중립 색, axe, 가로 넘침 없음을 확인한다.
- PC와 iPhone 크기에서 자동 확인의 최근 실행(가격 셈과 가격 이유가 있는 실행 포함)과 이전 가격 줄이 있는 상세를 캡처해 읽었다. 처음 캡처에서 iPhone 크기의 이전 가격 줄이 낱말 가운데서 줄을 바꿔("보여줘 / 요.") 낱말 단위로 바꾸게(`word-break: keep-all`) 고친 뒤 다시 캡처했다. 실행 줄은 PC에서 시각 오른쪽에, iPhone 크기에서 시각 아래 한 줄로 들어간다. 캡처용 검사는 커밋하지 않았다.

각 단계의 Red는 `docs/evidence/price-check/red-*.txt`에 있다.

- `red-domain.txt`: `decidePriceCheck`가 같은 서명으로 늘 `internal`을 낼 때 7개가 실패한다.
- `red-lists-unit.txt`: 새 마이그레이션이 없어 SQL의 두 이유 목록 검사가 실패한다.
- `red-sql-missing.txt`: 새 마이그레이션이 없어 가격 확인 23개와 catalog 4개가 실패한다(가격 분기가 없어 `none`, 열 없음). 통과한 하나는 권한 밖 거절이라 전후 모두 성립한다.
- `red-sql-defects.txt`: 결함 넷을 한꺼번에 넣었을 때 각 규칙을 지키는 검사 넷만 실패한다. 서울 날짜 대신 24시간, 정산이 `title`을 씀, 다른 통화도 확인으로 씀, 울타리에서 구매 상태를 뺌이다.
- `red-sql-owner-title.txt`: 정산에 `owner_title = null`을 넣으면 작업 역할에 권한이 없어 42501로 실패하고 확인 정산 검사 셋이 실패한다.
- `red-run-unit.txt`: 실행의 가격 분기가 같은 서명으로 아무것도 하지 않을 때 8개가 실패한다. 수집 검사 16개는 바꾼 구조에서 통과한다.
- `red-adapter.txt`: 어댑터의 `price`가 예외를 던지고 `next`가 가격 확인을 읽지 못할 때 어댑터 검사가 실패한다.
- `red-service.txt`: 실행의 가격 분기를 비우면 service 둘이 실패한다. 구매완료 상품을 읽지 않는다는 검사는 고르기를 지키는 검사라 그대로 통과한다. 처음 기록은 테스트가 공유 키를 두 번 만들어 다른 이유로 실패해, 테스트를 고친 뒤 다시 실행했다.
- `red-contract.txt`: 어댑터와 응답 변환이 `priceCheck`를 null로 채우고 실행 계약이 수집 이유만 받을 때 처리기 둘과 OpenAPI 일치 검사, 보관함 읽기 persistence 하나가 실패한다.
- `red-screen-unit.txt`: 화면의 이전 가격 줄·실행 줄·가격 이유·합치기가 같은 서명의 대역일 때 8개가 실패한다.
- `red-http.txt`: 가격 분기를 비운 빌드에서 새 HTTP 검사가 실패한다(소스는 되돌려 persistence·service는 통과).
- `red-browser.txt`: 화면의 가격 줄을 뺀 빌드에서 새 브라우저 검사가 두 기기 모두 실패하고 기존 48개는 통과한다.
- 기존 검사 중 바꾼 것. catalog 셋(`worker-runs.test.ts`의 함수·권한, `share-add.test.ts`의 익명 실행 목록, `library-security.test.ts`의 공개 함수 목록)에 새 함수와 권한을 더했다. 실행 줄의 기대 문구에 "· 가격 확인 0"이 붙었다. 상품 고정값에 `priceCheck: null`을 더했다. 수집 실행 service 검사의 실패 코드 타입을 가져오기 코드로 좁혔다.

## 검토

이 기록은 구현 담당자가 썼다. 구현에 참여하지 않은 검토자의 독립 검토는 아직 하지 않았다. 검토와 조정자 검증은 이 PR의 다음 단계다.

## 남은 범위

- 옵션마다 가격이 다른 페이지는 `no_single_price`로 이전 가격을 지킨다. 다른 옵션의 가격 하나만 보이는 페이지는 알아낼 수 없다(3a부터의 한계).
- 처리량. 수집과 가격 확인은 실행당 60개를 나눠 쓰고, 실행당 실제 처리량(추정 25~45개)은 측정하지 않았다. 그보다 큰 보관함은 오래 확인하지 않은 것부터 하루보다 드물게 확인한다.
- 소유자의 수집이 가격을 쓰지 못한 상품은 같은 날 작업자가 한 번 더 읽는다(설계 선택).
- 끊긴 실행이 고른 확인은 이유 없이 다음 서울 날짜를 기다린다. 그동안 상세에는 줄이 없고 카드의 마지막 확인 날짜만 남는다.
- 서울 자정 직전에 고르고 자정 뒤에 정산한 확인은 다음 날 확인으로 남는다.
- 열어 둔 탭은 예약 실행의 결과를 새로고침해야 보인다(4c·5a와 같은 후속).
- 유출된 작업 키는 5a의 힘에 더해 대상 상품의 오늘 확인을 소진하고 가격이나 이유를 위조할 수 있다. 이름·소유자 열·구매·사진·키는 건드리지 못하고, 화면에서 폐기하면 바로 멈춘다.
- 실제 쇼핑몰의 가격 페이지, GitHub 예약 실행(지연·누락·60일 비활성 정지), 호스팅의 `maxDuration`·`Authorization` 전달·배포 보호, 운영 Storage·Supabase 로그, 데이터센터 IP를 막는 쇼핑몰은 확인하지 않았다. 워크플로는 이 PR에서 한 번도 실행하지 않았다.
- 소유자의 실행기는 3a부터 구매완료 상품의 가격도 쓴다(작업자는 쓰지 않는다). 이 단위는 그 동작을 바꾸지 않았다.
- 가격 알림과 가격 이력은 범위 밖이다.
