# 정기 수집과 전용 작업 키 (5a)

소유자가 moti를 열지 않아도 하루 세 번 아직 가져오지 못한 상품 정보를 가져오게 하는 단위다. GitHub Actions가 한국 시간 06:17·14:17·22:17에 moti를 부르고, moti는 대기 중이거나 멈췄거나 다시 해 볼 만한 실패로 끝난 위시 상품의 이름과 가격을 가져온다. 예약 작업은 공유 키나 소유자 세션이 아니라 전용 작업 키를 쓰고, 그 키는 작업자의 단계만 실행한다. 구매완료 상품과 소유자가 고친 이름(`owner_title`)은 건드리지 않고, 실행은 겹치지 않으며, 시도는 소유자와 함께 세 번까지다. 소유자는 "자동 확인" 창에서 각 실행이 무엇을 했는지 본다. 이전에는 링크를 담은 뒤 소유자가 moti를 열어야만 수집이 시작됐다.

이 PR은 5단위를 나눈 첫 번째다. 매일 가격 확인(5b)과 남은 사진 정리(5c)는 다음 PR이다.

## 바뀐 동작

- 마이그레이션 `20261117000000_scheduled_runs.sql` 하나에 이 단위의 SQL이 있다.
  - `moti.worker_keys`는 4c의 저장 키와 같은 모양이다. SQL이 `moti_wk_`와 `gen_random_bytes(32)`의 base64url 43자로 비밀을 만들고 SHA-256(`token_hash`)과 끝 네 글자(`hint`)만 남긴다. 비밀은 만든 응답에만 한 번 담긴다. 소유자당 활성 키는 하나이고, 폐기한 행은 남아 화면이 언제 폐기했는지 보인다. 접두사가 공유 키(`moti_sk_`)와 달라 두 경로의 형식 검사가 서로의 키를 거절한다.
  - `moti.worker_runs`는 실행 하나당 한 행이다. 열린 행(`finished_at`이 null)이 실행 임대(90초)이고, 소유자당 하나뿐이다(부분 고유 인덱스). 정산할 때마다 수집·실패 셈과 이유별 실패(`failures`, 닫힌 목록의 코드와 횟수뿐)가 오르므로, 끊긴 실행도 그때까지의 셈을 남긴다. 멈춘 이유는 `done`(남은 일 없음), `deadline`(남은 일을 다음 실행에 넘김), `cut`(임대가 끝나도록 끝내지 못함), `revoked`(키 폐기로 멈춤)다. 가격 셈(`prices_confirmed`·`prices_kept`)은 5b를 위해 지금 0으로 만든다.
  - 소유자 RPC 세 개(`moti_rpc` 소유, `authenticated`만, `require_owner`). `moti_worker_read`는 활성 키(없으면 마지막으로 폐기한 키, 없으면 null)와 최근 실행 다섯 개를 돌려준다. 임대가 끝난 열린 실행은 임대가 끝난 때 `cut`으로 읽는다. `moti_worker_key_issue(p_replaces)`는 화면이 본 활성 키일 때만 바꾸고(아니면 `M0008`), `moti_worker_key_revoke(p_key_id)`는 멱등이며 없는 키는 `M0016`이다. 바꾸기와 폐기는 그 키의 열린 실행을 바로 닫는다. `moti_rpc`는 키 해시와 실행 임대 토큰을 읽지 못한다. 백업과 복원은 두 테이블을 건드리지 않는다.
  - 새 역할 `moti_worker`(로그인 불가, 상속 없음, RLS 우회 없음, 구성원은 `postgres`뿐)가 익명이 실행하는 작업 단계 다섯 개(`public.moti_worker_begin`·`next`·`complete`·`fail`·`finish`)를 소유한다. 이 역할의 권한이 울타리이고 catalog 테스트가 정확한 목록을 고정한다. 소유자 설정의 두 열 읽기, 자기 활성 키 찾기와 사용 기록, 자기 실행 행, 수집 작업의 이름 붙은 열 읽기·쓰기, 상품의 링크·구매 상태·저장한 가격의 통화 읽기와 수집 열(`title`, 수집 단계, 사진 결과, 마지막 성공 가격) 쓰기, 제약조건이 부르는 검사 함수 실행이다. `owner_title`·메모·옵션·revision·구매 열·사진 사본 열, 컬렉션·소속·공유 키·Storage, 다른 함수는 없다. 함수는 열 이름을 적고 `*`를 쓰지 않는다.
  - `begin(p_key)`는 키 형식, 활성 키, 설정된 소유자의 Google 연결을 SQL에서 본다. 모르거나 형식이 다르거나 폐기했거나 공유 키이거나 소유자 설정이 바뀐 키는 모두 같은 `M0012`다. 임대가 끝난 열린 실행을 그때 `cut`으로 닫고, 30일이 지난 실행을 지우고, 24시간 안에 여덟 번 시작했으면 `M0015`, 임대가 살아 있는 실행이 있으면 `M0014`다. 거절된 시작은 함께 되돌아가 키의 마지막 사용 시각도 바뀌지 않는다.
  - 나머지 단계는 같은 검사(`moti.worker_run_owner`)로 시작한다. 키 형식, 활성 키, 그 키의 실행, 열려 있음, 같은 임대, 임대가 남음 순서이고 키는 `M0012`, 실행은 `M0013`이다. 실행 행을 잠그므로 폐기는 진행 중인 단계를 기다리고, 폐기 뒤의 다음 단계는 `M0012`다. 단계가 키를 확인한 뒤 실행 행을 기다리는 사이 폐기가 커밋돼 실행이 닫혔으면 키를 다시 보아 `M0012`로 답한다.
  - `next`는 지금 세대의 작업 중 위시 상품이고 시도가 3번 미만이며 대기, 임대가 끝난 실행, 한 시간 전에 다시 해 볼 만한 이유(`dns_failed`, `connect_failed`, `timeout`, `blocked_by_site`, `http_status`, `internal`)로 실패한 작업 하나를 고른다. 대기 작업 먼저, 그다음 최신 상품이다. 다른 요청이 잠근 작업은 건너뛰고(`skip locked`), 소유자의 `metadata_claim`과 같이 시도를 올리고 60초 작업 임대를 잡는다. 답은 작업 id·작업 임대·링크뿐이고 사진 객체 이름은 없다. SQL의 재시도 목록은 TypeScript의 다시 시도할 수 있는 수집 이유에서 시도 소진을 뺀 것과 같고 단위 테스트가 마이그레이션을 읽어 확인한다.
  - `complete`는 이름을 `title`에만 쓴다. 소유자가 고친 이름, revision, 화면 이름은 그대로다. 가격은 위시이고 저장한 가격이 없거나 같은 통화일 때만 쓴다. 정산 사이에 구매완료로 옮긴 상품은 이름만 쓴다. 페이지에 사진 주소가 있으면 사진 결과를 `waiting`, 없으면 `absent`로 두고 이전 사본은 그대로 보인다. `fail`은 닫힌 목록의 이유(시도 소진 제외)로 작업과 상품을 실패로 둔다. 세대가 바뀌었거나 작업 임대가 다르면 둘 다 `stale`이고 아무것도 쓰지 않는다. 답은 `applied`·`stale`뿐이다.
  - `finish(p_stop)`는 `done`이나 `deadline`으로 실행을 닫고 셈을 돌려준다.
  - `moti_metadata_wake`가 넓어졌다. 시도 0인 대기 작업을 깨운 뒤 같은 한도(8개) 안에서 사진이 `waiting`인 상품을 최신부터 새 세대로 대기열에 다시 둔다(`metadata_retry`와 같은 재대기). 다른 요청이 잠근 상품은 건너뛴다. 작업 다음에 상품을 잠가 작업 → 상품 순서를 지킨다.
- 예약 실행 경로는 `POST /api/scheduled-runs`(`maxDuration = 60`)다. `Authorization: Bearer moti_wk_<43자>`만 읽고 본문과 쿠키는 읽지 않는다. 조립 위치 `src/app/_server/worker-context.ts`는 쿠키 없는 익명 클라이언트(단계마다 5초)를 만든다. ESLint가 이 파일과 경로에서 `next/headers`·`@supabase/ssr`·쿠키 컨텍스트·사진 모듈을, `src/features/worker`에서 사진 모듈을 막는다. 응답은 `no-store`이고 쿠키와 CORS 허용 헤더는 없다.
  - 실행은 요청 안에서 끝나 GitHub가 결과를 본다. `begin` 뒤 세 줄이 처음 20초 동안만 새 작업을 고르고(최대 60개), 엄격한 가져오기 정책으로 페이지(15초)를 읽어 이름과 가격을 정산한 뒤 `finish`한다. 최악은 5 + 20 + (5 + 15 + 5) + 5 = 55초다. 모든 줄이 남은 일이 없다고 보면 `done`, 아니면 `deadline`이다. 키가 거절되거나 임대를 잃으면 모든 줄을 멈추고 `finish`하지 않는다. 한 줄에서 두 단계가 이어 실패하면 그 줄만 멈추고 그 작업은 작업 임대에 남긴다.

  | 경우 | 상태·코드 |
  | --- | --- |
  | 실행을 마침 | 200 `{ stop, collections: { collected, failed }, prices: { confirmed, kept }, failures }` |
  | 키 없음·형식 다름·공유 키·소유자 쿠키만·모름·폐기·실행 중 폐기 | 401 `worker_key_rejected`(같은 바이트, `WWW-Authenticate: Bearer`) |
  | 다른 실행이 임대를 쥠·실행 중 임대를 잃음 | 409 `run_busy`·`run_lost` |
  | 24시간에 여덟 번 | 429 `run_limit` |
  | 설정 없음·저장소 | 503 `unconfigured`·`unavailable` |
- 소유자 경로는 보관함 관문(쓰기는 같은 출처, 세션, Google 소유자)을 지난다. `GET /api/worker-keys`는 `{ key, runs }`, `POST /api/worker-keys { replaces }`는 201 `{ key, secret }`(`no-store`), 오래된 화면은 409 `revision_conflict`, `DELETE /api/worker-keys/{keyId}`는 200 폐기한 키, 없는 키는 404 `worker_key_missing`(새 오류 코드)이다. 작업 키만 보내고 쿠키가 없는 요청은 모든 소유자 경로에서 401 `signed_out`이다.
- `docs/api/openapi.json`을 다시 생성했다. 예약 실행 경로는 `workerKey` bearer 보안 체계를 쓴다.
- 실제 화면에 "자동 확인" 대화상자가 생겼다. PC 사이드바의 "백업과 복원" 아래와 모바일 상단 아이콘에서 연다.
  - 머리말은 하루 세 번(오전 6:17, 오후 2:17, 오후 10:17) GitHub Actions가 부르며 GitHub이 늦추거나 건너뛸 수 있다고 말한다.
  - 작업 키 패널은 4c의 저장 키 패널과 같은 로직과 모양이다(1번 커밋이 패널을 엔드포인트를 받게 바꿨다). 키 없음("아직 작업 키가 없어요."), 한 번 보이는 키(`moti_wk_…`, "키 복사", "붙여 넣었어요"), 활성 키("작업 키 ••••Wk9_ · 11월 13일 만듦"과 "아직 이 키로 실행한 적이 없어요." 또는 "마지막으로 이 키로 실행을 시작한 때: …"), 폐기한 키를 보인다. 바꾸기와 폐기는 패널 안 확인이 "취소"에 초점을 두고, 진행 중인 실행도 멈춘다고 말한다. 비밀은 "붙여 넣었어요", 창 닫기, 뒤로 가기 캐시 복귀에서 사라진다.
  - "GitHub에 넣을 값"은 비밀값 `MOTI_WORKER_TOKEN`과 변수 `MOTI_WORKER_URL`(이 배포의 주소)을 "이름 복사"·"주소 복사"와 함께 보이고, 둘 다 넣기 전에는 예약 실행이 건너뛴다고 말한다.
  - "최근 실행"은 다섯 개까지 서울 시각, "수집 3 · 실패 1", 멈춘 이유("할 일을 모두 마쳤어요.", "남은 일은 다음 실행에서 이어가요.", "끝까지 실행되지 못했어요.", "키를 폐기해 멈췄어요.", "실행 중이에요.")와 이유별 실패 횟수를 보인다. `cut`만 오류 색이다. 활성 키가 있는데 키를 만든 뒤나 마지막 실행 뒤 26시간이 지나면 "26시간 넘게 실행 기록이 없어요. GitHub 예약 실행이 늦거나 멈췄을 수 있어요."라고 알린다. "사진은 moti를 열 때 가져와요."로 끝난다.
  - "연결됨", "연결 완료", "설치 완료"는 어디에도 없다. 화면은 GitHub에 값을 넣었는지 알 수 없다. 키가 실행을 시작한 때만 증거로 보이고 그렇게 이름 붙였다.
- 사진이 `waiting`인 상품의 카드는 중립 자리표시 "사진을 가져오는 중"(이전 사본이 있으면 그 사본)을, 상세는 "상품 정보를 가져왔어요"와 "사진은 곧 가져와요."를 보인다. 화면은 처음 받은 보관함에 시도 0인 대기 상품이나 사진을 기다리는 상품이 있으면 깨우기를 부르고, 응답 뒤 소유자의 실행기가 페이지를 다시 읽어 사진을 소유자 토큰으로 복사한다.
- `.github/workflows/scheduled-run.yml`과 `scripts/scheduled-run.sh`. 예약은 `17 21 * * *`, `17 5 * * *`, `17 13 * * *`(UTC)이고 `workflow_dispatch`가 있다. `contents: read`, `timeout-minutes: 3`, 겹치지 않는 `concurrency`, `persist-credentials: false`다. PR·push 트리거가 없어 필수 검사가 되지 않는다.
  - 스크립트는 두 값 중 하나라도 비었으면 `::notice::`만 남기고 0으로 끝난다. 주소는 `https://호스트[:포트]`(경로 없음), 키는 작업 키 형식이어야 한다. 키는 curl의 표준 입력 헤더(`--header @-`)로만 보내고 명령줄과 로그에 남기지 않는다. `--proto '=https'`, `--max-time 75`이며 리다이렉트를 따르지 않는다.
  - 저장소가 공개라 Actions 로그도 공개다. 그래서 200은 `stop`이 `done`·`deadline`인지만 확인하고 정해진 문구("실행을 마쳤어요." 또는 "실행 시간이 다 돼 멈췄어요. 남은 일은 다음 실행에서 이어가요."와 "결과는 moti의 자동 확인에서 볼 수 있어요.")만 기록한다. 셈과 실패 이유는 자동 확인에만 있다. 모양이 다른 200은 서버 글자 없이 오류로 1로 끝난다. 409는 알림, 429는 경고이고 둘 다 0으로 끝난다. 401은 새 키를 만들어 비밀값을 바꾸라는 오류, 그 밖의 상태와 연결 실패는 오류로 1로 끝난다. 서버가 보낸 글자는 형식을 검사한 오류 코드(`^[a-z_]{1,40}$`)만 내보내므로 응답 본문이 워크플로 명령을 흉내 내도 명령이 되지 않는다. 주소 끝의 `/` 하나는 떼고 받는다.

## 소유자가 GitHub에 넣을 값

이 PR은 아무것도 설정하지 않는다. 소유자가 두 값을 넣기 전에는 예약 실행이 시작되지만 알림만 남기고 건너뛴다.

| 위치 | 이름 | 값 |
| --- | --- | --- |
| 저장소 Settings → Secrets and variables → Actions → Secrets | `MOTI_WORKER_TOKEN` | moti의 "자동 확인"에서 만든 작업 키(`moti_wk_`로 시작하는 51자) |
| 같은 곳의 Variables | `MOTI_WORKER_URL` | 운영 배포의 주소(`https://<도메인>`, 경로 없음). 화면이 지금 연 배포의 주소를 보인다. |

호스팅에는 새 환경 변수가 없다(기존 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `MOTI_OWNER_GOOGLE_SUBJECT`). 함수 실행 시간 60초를 허용하는 요금제가 필요하다. 키를 바꾸면 GitHub 비밀값도 바꿔야 하고, 그 사이의 실행은 401로 실패한다.

| 기준 | A. 전용 작업 키 | B. 소유자 위임 |
| --- | --- | --- |
| 자격 | `moti_wk_` 키(해시만 저장)를 GitHub 비밀값에 둔다 | 두 번째 Google 로그인으로 만든 소유자 세션의 refresh token을 호스팅 환경의 키로 봉인해 DB에 두고, GitHub에는 실행 트리거 키 |
| DB 권한 | 전용 역할 `moti_worker`의 열 단위 권한(catalog 고정) | 세션 id로 예약 세션을 알아보고 `require_owner`가 기본으로 거절, 허용 목록의 래퍼만 받음 |
| Storage | 닿지 않는다. 사진과 정리는 소유자가 열 때 | 소유자 JWT로 직접 복사·정리 |
| 새 부분 | 테이블 둘, 역할 하나, 익명 RPC 다섯, 소유자 RPC 셋, 경로 셋 | 테이블 셋, 역할 하나, 익명 RPC 둘, OAuth 콜백, 봉인 키, `require_owner`·`owner_or_null` 변경 |
| 깨지는 경우 | 키 폐기나 교체 | 실행마다 토큰 회전. 답 하나를 잃으면 다음 실행이 재사용 감지로 세션을 잃고, 소유자의 로그아웃(`signOut()` 기본 `global`)도 위임을 끊는다 |
| 유출의 힘 | 하루 8번 실행, 대상 링크 읽기, 시도 소진, 수집한 이름·가격 위조. 소유자 열·Storage·키·컬렉션은 없음 | 트리거와 봉인 키를 함께 가지면 Auth API에서 소유자와 같은 세션(`updateUser`, identity 연결) |

A를 바탕으로 합친 설계를 따랐다(계약 `5-design.md`).

- Storage는 요청의 JWT로만 권한을 정한다. 소유자 JWT 없이 사본을 쓰려면 서비스 키나 JWT 비밀이 필요하고 둘 다 금지다. 두 후보 모두 이것을 찾았다. 그래서 작업자는 Storage를 부르지 않고 사진을 `waiting`으로 두며, 소유자의 기존 깨우기가 사진을 복사한다. 사진 경로는 3b가 고른 하나로 남는다.
- B의 위임 세션은 SQL 울타리가 닿지 않는 Auth API에서 소유자와 같다. 두 번째 OAuth 로그인, 봉인 토큰, 호스팅의 봉인 키가 필요하고 실행마다 회전해 답 하나를 잃으면 깨진다. A의 키는 더 좁고 화면에서 바꿀 수 있으며 catalog가 고정한 권한이 울타리다.
- B에서 옮긴 것. moti의 로그아웃은 auth-js의 기본 `global` 범위다(B가 2.119.0 원본에서 확인). 작업 키와 무관하고 키는 일부러 로그아웃 뒤에도 남는다. 실행을 멈추는 방법은 키 폐기다. GitHub의 실패 메일은 워크플로를 마지막으로 고친 사람에게 가므로 화면의 26시간 알림이 앱 안의 신호다. B가 제안한 5a·5b 분리를 그대로 따랐다.
- 두 비밀 분리(트리거만 GitHub, DB 키는 호스팅 환경)는 위조 능력을 GitHub에서 호스팅으로 옮기는 강화다. 교체가 화면 한 번에서 환경 변경과 재배포로 바뀌어 만들지 않고 선택지로 남겼다.

두 후보는 같은 모델 계열에서 독립적으로 작성했고 조정자가 합쳤다. 다른 계열 심사는 제공되지 않아 생략했다.

### 전달 분리

5단위는 PR 셋으로 나눈다. 각 PR은 4a~4c와 같이 구현, 독립 검토, 조정자 검증, 시험한 head에 고정한 squash 자동 병합을 거친다.

- 5a(이 PR). 정기 수집. 키, 실행 임대와 기록, 작업 역할, 수집 단계, `waiting` 사진과 깨우기, 자동 확인 창, 워크플로와 스크립트.
- 5b. 매일 가격 확인. 상품 열 `price_checked_at`·`price_check_code`, `next`의 가격 분기, `moti_worker_price`, `decidePriceCheck`, 상세의 이전 가격 유지 줄. 변경 기록 `price-check.md`.
- 5c. 열 때 남은 사진 정리. `moti.stored_pictures`, `moti_picture_orphans`, 깨우기 `after()`의 `sweepPictures`. 변경 기록 `picture-sweep.md`.

`next`는 수집 아니면 `none`을 돌려주는 모양이라 5b는 가격 분기와 셈만 더한다. 실행 행과 API 응답에는 가격 셈이 이미 0으로 있다.

### 설계와 다르게 구현한 것

- 화면은 모든 첫 로드가 아니라 시도 0인 대기 상품이나 사진을 기다리는 상품이 있을 때만 깨운다. 모든 로드의 깨우기는 정리(5c)가 필요로 하는 것이라 5c에서 바꾼다.
- 바꾸기·폐기가 닫는 열린 실행 중 임대가 이미 끝난 것은 `revoked`가 아니라 임대가 끝난 때의 `cut`이다. 실제로 일어난 일이 끊김이기 때문이다.
- 소유자 읽기의 실행 상태 칸은 `state`이고 진행 중인 실행은 `running`이다.
- `fail`은 시도 소진(`attempts_exhausted`)도 거절한다. 작업자는 그 이유를 만들지 않는다.
- 실행의 줄은 `next` 전에 자리를 잡아 60개 한도가 정확히 지켜진다. `next`가 없음이나 오류를 주면 자리를 돌려준다.
- 깨우기는 구매 상태와 상관없이 사진을 기다리는 상품을 다시 수집한다. 구매완료 상품도 사진은 필요하고 사진은 소유자의 실행기만 복사할 수 있기 때문이다. 그 실행기는 3a부터와 같이 구매완료 상품의 가격도 쓸 수 있다(작업자는 쓰지 않는다). 검토 뒤 이 선택을 persistence 검사로 고정했다.
- `src/features/worker`의 사진 모듈 금지는 `no-restricted-syntax`다. 같은 파일에 나중 `no-restricted-imports` 블록을 두면 계층 규칙을 덮어쓴다.
- 커밋은 계약의 아홉이 아니라 열한 개다. A의 SQL과 HTTP 커밋을 키·실행 임대·수집 단계와 소유자 경로·작업 경로로 더 나눴고, 시각 확인 뒤 대화상자 배치를 고친 커밋(`72889ef`)이 있다.
- 실제 HTTP와 실제 스택 브라우저는 실행을 루프백 링크(`http://127.0.0.1:9/…`)로 증명한다. 앱의 정책이 거절해 `blocked_address`로 끝난다. 이름·가격·`waiting`과 소유자의 사진 복사는 service 검사가 고정 페이지와 실제 DB·Storage로 증명한다.

- persistence는 작업 키(형식, 해시, 끝 네 글자, 비밀이 어느 열에도 없음, 오래된 화면과 동시 만들기의 `M0008`, 멱등 폐기, `M0016`, 익명과 다른 계정의 거절, 해시·임대 토큰을 읽지 못하는 `moti_rpc`, 백업·복원과의 분리, 바꾸기·폐기가 닫는 열린 실행), 실행 시작(90초 임대, 거절되는 키 열 가지와 소유자 설정 변경 두 가지의 같은 `M0012`, 동시 시작의 `M0014`, 임대가 끝난 실행의 `cut`, 아홉 번째의 `M0015`, 30일 보관), 끝내기와 단계 검사(`M0013`·`M0012`·`M0002`), 실행 중 폐기, 로그인 세션의 실행 거절, PostgREST의 Bearer 키 거절, 공유 키 함수의 작업 키 거절, 작업 역할의 속성·구성원·소유 함수·권한·정책 목록과 고정 권한 밖의 42501 스물여덟 가지(`owner_title`·메모·구매·사진 열·컬렉션·키·Storage·소유자 함수), 수집 집기(대상과 순서, 세대·시도·임대·재시도 시각·이유 조건, 잠긴 작업 건너뛰기), 결과 쓰기(`title`만, 소유자 이름·revision·화면 이름 유지, `waiting`·`absent`, 이전 사본 유지, 다른 통화와 정산 중 구매완료의 가격 유지, Storage 객체 없음), 실패와 이유별 셈, `stale`, 잘못된 결과의 `M0002`, 두 어댑터의 값과 오류 변환, 사진을 기다리는 상품 깨우기(새 세대, 한도 공유, 잠긴 상품 건너뛰기)를 확인한다.
- service는 키로 담고 아무도 열지 않은 상품을 작업 키로 수집해 이름·가격·`waiting`을 쓰고 Storage 객체를 만들지 않는 것, 막힌 쇼핑몰의 이유 기록과 폐기한 키의 거절, 소유자가 열 때 깨워 소유자 세션으로 비공개 사본을 만드는 것을 실제 DB·Storage·sharp와 고정 페이지(쇼핑몰만 바꿈)로 확인한다.
- 실제 HTTP는 작업 키 없음·공유 키·소유자 쿠키·모르는 키의 같은 401, 루프백 링크의 `blocked_address`와 셈, 다른 실행의 409와 여덟 번 뒤의 429, 작업 키로 소유자 경로 여섯 곳을 부른 401 `signed_out`과 DB 그대로, 소유자 키 관리의 201·409·404·403·400을 확인한다.
- 실제 스택 브라우저 세 흐름을 두 기기에서 실행한다. 작업 키를 한 번만 보고 창을 닫았다 열면 사라지며, Node `fetch`로 GitHub처럼 실행한 뒤 다시 열면 기록과 실행을 시작한 때가 보인다. 바꾸기·폐기 확인이 "취소"에 머물고 Esc가 확인만 닫으며 이전 키와 폐기한 키는 401이다. 키가 없을 때와 보일 때와 기록이 있을 때 axe 검사, 중립 색, PC의 키보드 초점 고리, `cut`만 오류 색, 26시간 알림, 가로 넘침 없음을 확인한다.
- 단위는 키 형식과 헤더 읽기, 실행의 줄·시간 창·60개 한도·멈춤·실패 처리(가짜 저장소와 시계), 예약 경로 처리기(Given–When–Then), 소유자 키 처리기, SQL 재시도 목록과 TypeScript 목록의 일치, 화면 상태·문구·API 클라이언트, 워크플로(예약 시각을 서울 시각으로, 트리거·권한·시간 한도·값 전달)와 스크립트(가짜 `curl`로 건너뛰기·형식 거절·표준 입력의 키·상태별 종료 코드·서버 글자를 내보내지 않음)를 확인한다.
- PC와 iPhone 크기에서 키 없음, 한 번 보이는 키, 끊긴 실행과 26시간 알림이 있는 활성 키, 바꾸기 확인, 폐기 확인, 폐기한 키, 사진을 기다리는 카드와 상세를 캡처해 읽었다. 처음 캡처에서 목록이 브라우저 기본 들여쓰기로 밀리고 실패 이유가 "…막았어요. 1건"처럼 한 줄에 붙어 읽혀, 목록을 섹션 가장자리에 맞추고 이유마다 한 줄("1건 · …")로 바꾼 뒤 다시 캡처했다(`72889ef`). 캡처용 검사는 커밋하지 않았다.

- 기존 catalog 검사(`share-add.test.ts`의 익명 실행 함수 목록, `library-security.test.ts`의 테이블·공개 함수 목록)는 작업 테이블과 함수를 더하며 목록을 고쳤다. 4c의 키 패널 검사는 이벤트 이름만 `key.*`와 `endpoint`로 바꾸고 의미는 그대로다.

## 검토

이 기록은 구현 담당자가 썼다. 구현에 참여하지 않은 검토자가 head `fc3ad90`의 설계 계약, 전체 diff, 이전 마이그레이션과 모든 계층의 테스트, 화면 캡처를 읽었다. 검토자는 DB와 서버가 필요 없는 단위 검사만 돌렸고, 실제 스택 검사는 조정자가 같은 head에서 `npm run verify`(종료 0)로 다시 확인했다.

- 병합 전에 고쳐야 할 결함은 없었다. 작업 역할의 권한과 익명 실행 목록은 catalog가 정확히 고정하고 `owner_title`·구매·사진 열·Storage 권한이 없다. 키는 SQL에서 해시로 비교하고 모든 거절이 같은 `M0012`와 같은 바이트의 401이다. 열린 실행은 하나이고 잠금 순서(실행 → 작업 → 상품, 키 → 실행)에 순환이 없다. 늦은 `complete`는 세대와 작업 임대를 확인해 소유자의 새 수집을 덮지 않는다. 실행은 예외를 던지지 않고, 워크플로는 키를 표준 입력으로만 보낸다.
- 권고를 반영했다.
  - 키를 새로 만들거나 바꾼 뒤 패널이 다시 읽는다. 바꾸기가 멈춘 실행이 창을 다시 열 때까지 "실행 중이에요."로 남았다.
  - `next`가 실패한 줄이 60개 한도의 자리를 돌려주는 것을 검사한다. 이전에는 그 줄을 지워도 모든 검사가 통과했다.
  - 단계가 키를 확인한 뒤 실행 행을 기다리는 사이 폐기가 커밋되면 409 `run_lost`가 아니라 401이 되도록 키를 다시 본다. 커밋하지 않은 폐기 트랜잭션으로 경쟁을 재현하는 persistence 검사를 더했다.
  - 저장소가 공개라 예약 실행 로그에 셈과 실패 이유를 남기지 않고 정해진 문구만 남긴다. 모양이 다른 200은 오류로 끝내고, 주소 끝의 `/`는 떼고 받는다.
  - 공유 경로가 작업 키를 접두사로 거절하는 처리기 검사, 작업 역할에 `owner_title` 쓰기를 더하면 catalog 검사 둘이 실패한다는 증거, 구매완료로 옮긴 사진 대기 상품도 깨운다는 검사를 더했다. `docs/backend-implementation.md`의 익명 예외 문단이 어느 함수를 말하는지 고쳤다.
  - 각 Red는 `docs/evidence/scheduled-runs/red-review-*.txt`에 있다.
- 나머지 지적(작업자와 소유자의 같은 페이지 다시 읽기, 정확히 60개로 끝난 실행의 `deadline`, 바꾸기 중 창을 닫았을 때, 남는 안내, 호스팅 여유 시간)은 아래 남은 범위에 적었다.

## 남은 범위

- GitHub 예약 실행. 늦거나 건너뛰는 일, 기본 브랜치에서만 실행되는 점, 공개 저장소에서 60일 동안 활동이 없으면 멈추는 점은 외부 동작이라 확인하지 않았다. 워크플로는 이 PR에서 한 번도 실행하지 않았다(`gh workflow run`도 하지 않았다). 앱 안의 신호는 26시간 알림뿐이다.
- 호스팅. 배포가 없다. 요금제가 `maxDuration = 60`을 지키는지, 프록시가 `Authorization`을 넘기는지, 배포 보호가 POST를 통과시키는지, 함수 지역과 Supabase 사이의 지연은 확인하지 않았다. 처리량(실행당 25~45개)은 추정이고 측정하지 않았다.
- 쇼핑몰이 데이터센터 IP를 막으면 `blocked_by_site`로 끝나고 한 시간 뒤 다음 실행이 다시 시도한다. 확인하지 않았다.
- 운영 Supabase. Storage 권한은 로컬과 같다고 가정한다. RPC 인자의 평문 키가 Postgres·API 로그에 남는지 확인하지 않았다(4c와 같은 열린 항목).
- 유출된 작업 키. 하루 8번 안에서 대상 상품의 링크를 읽고, 집기만 하고 정산하지 않아 시도를 소진시키고(그 뒤에는 소유자가 다시 가져오기), 수집한 이름과 가격을 위조할 수 있다. 소유자 열, 컬렉션, 구매, 사진, 키는 건드리지 못한다. 화면에서 폐기하면 바로 멈춘다.
- 사진. 작업자가 읽은 페이지는 소유자가 열 때 한 번 더 읽는다. 그 사이 사진은 "가져오는 중"이고, 열 때 깨우기는 8개까지라 나머지는 다음에 열 때 가져온다. 다시 읽기가 실패하면 상품은 실패로 바뀌고 이름은 남는다.
- 정리(5c 전까지). 끊긴 실행이나 실패한 지우기가 남긴 사진 사본은 아직 지우지 않는다. 작업자는 업로드하지 않아 새로 남기지 않는다.
- 가격(5b 전까지). 작업자는 수집하면서 가격을 쓰지만 이미 가져온 위시 상품을 매일 다시 확인하지 않는다.
- 시도 세 번을 다 쓴 작업은 "다시 가져오기"로 새 세대를 시작할 때까지 멈춤이나 실패로 남는다. 워크플로는 다시 시도하지 않으므로 실패한 실행은 8시간 뒤 다음 예약을 기다린다.
- 열어 둔 탭은 예약 실행의 결과를 새로고침해야 보인다(4c와 같은 후속).
- 실행 시간. 최악 55초에는 냉시작, 요청 조립, 응답 전송이 빠져 있다. `maxDuration`은 요청 시작부터 재므로 여유는 5초 안팎이고 호스팅에서 확인하지 않았다.
- 같은 페이지 다시 읽기. 소유자가 연 뒤 응답 뒤 작업이 40초 안에 다 못 한 사진 대기 상품은 대기로 남고, 다음 예약 실행이 먼저 집어 다시 `waiting`으로 둘 수 있다. 다음에 열 때 다시 깨워 결국 진행되지만 같은 페이지를 한 번 더 읽는다. 처리량이 문제가 되면 5c에서 다시 본다.
- 구매완료 상품. 작업자는 집지 않지만, 작업자가 수집한 뒤 구매완료로 옮긴 사진 대기 상품은 소유자가 열 때 깨워 사진을 복사하고 그 실행기가 페이지의 가격도 쓴다(3a부터의 소유자 실행기 동작).
- 남은 일이 정확히 60개였던 실행은 남은 일이 없어도 `deadline`("남은 일은 다음 실행에서 이어가요.")이다. 확인하려면 한도에 닿은 뒤 `next`를 한 번 더 불러야 해 그대로 두었다.
- 바꾸기 요청 중 창을 닫으면 새 비밀은 버려지고 이전 키는 이미 폐기돼, 소유자가 다시 바꾸기 전까지 예약 실행은 401이다. 패널의 안내("다른 곳에서 키가 바뀌었어요" 등)는 창을 닫았다 열어도 남는다. 둘 다 4c의 저장 키 패널과 같은 동작이다.
- 공개 저장소의 Actions 로그에는 실행 시각, 409·429 알림과 성공·실패 여부가 남는다. 셈과 이유, 링크, 이름은 남기지 않는다.
- 응답 뒤 작업(`after()`)의 실패는 4b·4c와 같이 기록하지 않는다. 남긴 것은 다음 예약 실행이 멈춘 작업을 다시 집고, 사진은 다음에 열 때 가져온다.
