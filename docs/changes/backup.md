# 보관함 백업과 복원 (4b)

소유자가 실제 보관함(`/`)을 파일 하나로 내려받아 두었다가 나중에 그 파일로 되돌리게 하는 단위다. Supabase 프로젝트를 잃었거나 정리를 잘못한 경우를 위한 것이다. 왕복은 소유자가 보거나 정한 값을 모두 지킨다. 링크와 옵션, 소유자 이름과 수집한 이름, 메모, 컬렉션 이름과 소속, 구매 상태와 구매일·실구매가(빈 값과 0원은 다르다), 담은 시각, 마지막 확인 가격이다. 유효하지 않거나 바뀐 파일은 아무것도 바꾸지 않는다. 복원은 파일 전체를 검사하고 소유자가 확인한 뒤 보관함을 바꾼다. 사진은 파일에 들어가지 않는다. 이전에는 실제 보관함의 데이터를 밖으로 꺼낼 방법이 없었다.

복원은 보관함 전체를 바꾸고, 파일은 데이터만 담으며, 확인 단계에서 바뀔 내용을 보여준다. 조정자가 정해 사용자에게 알린 기본값이다. 합치기 복원, 파일 안의 사진, 서명, 공유 키(4c)는 범위가 아니다.

## 바뀐 동작

- 백업 파일 형식은 `moti.library-backup` 버전 1이다. 정의는 `src/features/library/presentation/library-backup.ts` 한 곳에 있고 화면과 복원 경로가 같은 읽기 함수(`readLibraryBackup`)를 쓴다.
  - 담는 값은 `sourceUrl`, `option`, `collectedTitle`(수집한 이름), `ownerTitle`(소유자 이름, 없으면 null), `note`, 소속 컬렉션 이름 목록, `addedAt`, 구매(`wish` 또는 `purchased`와 구매일·실구매가), `lastSuccessfulPrice`(금액·통화·확인 시각)와 컬렉션의 `name`·`createdAt`이다.
  - id, revision, 수집 상태, 사진 열은 담지 않는다. 서버가 관리하는 상태라 파일이 정직하게 옮길 수 없다. 판별 주소(`identityUrl`)와 쇼핑몰은 링크에서 저장할 때와 같은 `parseLink`로 다시 만든다. 파일이 링크와 다른 판별 주소를 가질 수 없다.
  - 앱이 저장하는 값만 받는다. 링크·옵션·이름·컬렉션 이름은 공유 규칙 모듈로 정리한 값과 같아야 하고, 메모는 메모 규칙을 통과해야 한다. 시각은 API와 같은 밀리초 ISO 문자열이다. 모르는 칸, 형식이 다른 값, 추적 값만 다른 같은 링크, 대소문자만 다른 컬렉션 이름, 파일에 없는 소속 이름, 한 상품의 같은 소속 두 번, 범위 밖의 금액·날짜, 다른 형식은 거절하고 처음 문제의 위치(`products.12.sourceUrl`)를 알린다. 더 새로운 버전은 따로 알린다.
  - 한도는 파일 4MiB(`MAX_BACKUP_BYTES`, 호스팅 함수의 4.5MB 요청 한도 아래), 상품 5,000개, 컬렉션 500개, 상품당 소속 100개다.
  - 서명은 없다. "바뀐 파일"은 읽기 함수나 SQL이 거절하는 파일이다. 구조가 맞게 손으로 고친 파일은 소유자의 데이터로 복원한다. 서명 비밀값을 프로젝트와 함께 잃으면 소유자가 자기 백업을 읽지 못하게 되기 때문이다.
- 내보내기는 `GET /api/library/backup`이다. 새 RPC `moti_backup`이 수집한 이름과 소유자 이름을 따로, 소속을 컬렉션 이름으로 한 문장에서 읽는다(`product_json`은 두 이름을 합친다). 응답은 서울 시각 이름(`moti-backup-YYYYMMDD-HHmm.json`)의 첨부 파일이고 `no-store`, `nosniff`다. 오류는 JSON 응답이다. 파일은 밀리초 단위 시각과 파일이 가진 값으로 정렬해, 파일에서 복원한 보관함을 다시 내보내면 같은 순서가 된다.
- `moti_snapshot`은 새 `moti.library_json`을 돌려준다. 복원도 같은 함수를 돌려준다. 출력은 그대로다.
- 복원은 `POST /api/library/restore`다. 본문은 고른 파일의 글자 그대로이고 서버가 같은 읽기 함수로 다시 검사한다. `readJsonBody`에 한도 인자가 생겼고 복원만 4MiB, 나머지 쓰기는 16KiB를 지킨다. 같은 출처·세션·소유자 검사가 본문을 읽기 전에 끝나므로 소유자만 4MiB를 읽게 할 수 있다. 서버는 구매일을 자기 서울 날짜로 다시 검사한다. 성공은 200 `LibraryReadResponse`(바뀐 보관함)이고 새 오류 코드는 없다.

  | 경우 | 상태·코드 |
  | --- | --- |
  | 다른 출처 | 403 `cross_origin` |
  | JSON이 아님 | 415 `unsupported_media_type` |
  | 선언했거나 흘려보낸 본문이 4MiB 초과 | 413 `payload_too_large` |
  | 깨진 JSON, 백업이 아님, 더 새로운 버전, 바뀐 파일, 서버의 오늘보다 뒤의 구매일, SQL `M0002` | 400 `invalid_input`(`field`는 첫 문제 위치) |
  | 세션 없음·다른 계정·소유자 설정 없음 | 401·403·503 |
  | 잠금 대기 초과(`55P03`)·교착(`40P01`)·문 시간 초과(`57014`)·연결 | 503 `storage_unavailable` |
- `moti_restore_library`(보안 정의자, `moti_rpc` 소유, `authenticated`만 실행, `require_owner`)가 한 트랜잭션에서 보관함을 바꾼다.
  1. 잠그기 전에 입력 전체를 기존 쓰기 함수와 같은 규칙으로 검사한다. 하나라도 어긋나면 `M0002`다. 형 변환이나 DB 대조 규칙의 `lower()`가 거절한 값, 무결성 위반도 `M0002`로 바꾼다.
  2. 소유자별 권고 잠금으로 복원을 하나씩 실행하고, 수집 쓰기와 같은 순서(작업 → 상품, 그다음 컬렉션)로 행을 id 순서대로 잠근다. 잠금 대기는 5초까지다.
  3. 컬렉션은 이름(대소문자 무시)으로 맞춘다. 맞은 컬렉션은 id를 지키고 파일의 정확한 이름·만든 시각을 받고 revision이 오른다. 파일에 없는 컬렉션은 지우고 새 이름은 만든다.
  4. 상품은 링크 판별 값(`identity_hash`, 판별 주소와 옵션)으로 맞춘다. 맞은 상품은 id·수집 상태·수집한 이름·마지막 확인 가격·사진을 지키고, 링크 원문·소유자 이름·메모·구매·담은 시각을 파일 값으로 받고 revision이 1 오른다. 파일에 없는 상품은 지우고 그 사진 사본 이름을 돌려준다. 새 상품은 저장한 링크처럼 revision 1, 1세대 수집 대기로 들어가고 파일의 수집한 이름과 마지막 확인 가격을 받는다.
  5. 복원한 모든 상품의 소속을 파일의 이름으로 다시 만든다. 넣은 행 수가 파일의 소속 수와 다르면 `M0002`다.
  6. `{ library, replaced_pictures }`를 돌려준다.
- 응답 뒤(`after()`) `followUpRestore`가 지운 상품의 사진 사본을 소유자 토큰으로 버린다(`may_discard`가 허용한다, 1,000개씩). 그다음 수집을 기다리는 상품을 최근 것부터 두 개씩 수집하고, 40초가 지나면 새 수집을 시작하지 않는다. 남은 상품은 60초 뒤 멈춤으로 보이고 기존 "다시 가져오기"나 5단위 예약 작업이 처리한다. 순수 도우미 `runWithin`(시계 주입)은 예외를 던지지 않는다. 복원 경로의 `maxDuration`은 60초다.
- 화면은 PC 사이드바 로그아웃 위의 "백업과 복원"과 모바일 상단의 같은 이름 아이콘에서 대화상자를 연다.
  - "백업 만들기"는 백업을 받아 읽기 함수로 확인한 뒤 진짜 내려받기 링크를 보인다. iOS Safari는 await 뒤의 프로그램 내려받기를 막으므로 소유자가 링크를 누른다. 4MiB를 넘는 백업은 한 번에 복원할 수 없다고 알린다.
  - "백업 파일 선택"으로 고른 파일은 요청 전에 같은 읽기 함수로 검사한다. 확인 단계는 지금 보관함과 파일의 상품·컬렉션 수, 파일의 백업 시각, 파일에 없어 지워질 상품 수를 보이고 "취소"에 초점을 둔다. 파일에 상품이 없으면 보관함이 빈다고 알린다.
  - 만드는 중·읽는 중·바꾸는 중에는 대화상자가 닫히지 않는다(Esc와 닫기 무시). 다른 쓰기나 전체 다시 읽기가 진행 중이면 "보관함 바꾸기"가 꺼진다.
  - 성공하면 보관함을 응답으로 바꾸고(합치지 않는다) 위시 전체 보기로 돌아가 "보관함을 복원했어요. 새 상품의 사진은 차례로 다시 가져와요." 알림을 띄운다. 수집 대기가 있으므로 다시 읽기를 짧은 간격부터 다시 시작한다.
  - 400·413·415는 "보관함은 바뀌지 않았어요."를 붙인 오류다. 503·시간 초과·연결 끊김은 커밋 뒤 응답만 잃었을 수 있으므로 "복원을 마쳤는지 확인하지 못했어요. 최신 보관함을 불러왔어요. 필요하면 같은 파일로 다시 복원해 주세요."를 보이고 보관함을 다시 읽는다. 같은 파일을 두 번 복원해도 보이는 보관함은 같다.
  - 흰색·중립 회색·차콜만 쓰고 오류만 빨간색이다.
- 다른 탭에 새 규칙은 없다. 지워진 상품·컬렉션에 쓰면 기존 404·422 경로로 다시 읽는다. 맞은 상품은 revision이 올라 오래된 탭의 같은 revision 쓰기가 409가 되고, 늦은 주기적 읽기는 4a 규칙(낮은 revision 버림, 모르는 id 무시)으로 걸러진다.
- `docs/api/openapi.json`을 다시 생성했다. 백업 파일의 정리 값·교차 참조 규칙은 스키마 밖 검사라 문서에는 설명으로만 있다.

## 설계 선택

| 기준 | A. 한 번에 복원 | B. 서버에 올려 두고 적용 |
| --- | --- | --- |
| 흐름 | 화면이 파일을 읽어 개수를 보이고 글자 그대로 한 요청으로 보낸다. 서버가 다시 읽고 SQL 함수 하나가 한 트랜잭션에 적용한다. | 서버가 파일을 검사·예행해 소유자별 대기 복원(만료·지문·요약)으로 저장하고, 두 번째 요청이 적용한다. |
| 경로·저장 | 경로 2개, 새 테이블 없음 | 경로 3개, 대기 복원 테이블, 같은 SQL의 예행과 적용 |
| 기존 행 | 모두 지우고 새 id로 삽입. 사진은 다시 수집 | 맞는 행을 지키는 쪽을 열린 질문으로 남김 |
| 오래된 탭 | 새 id로 기존 404·422 경로 | 복원 뒤 revision을 화면이 본 값보다 높게 두는 하한 관리 |
| 파일 검사 | 화면과 서버가 같은 엄격한 읽기 함수 | 화면은 파일을 읽지 않고 서버 요약만 보임 |
| 새 오류 코드 | 없음 | "바뀌었음" 결과와 다시 확인 반복 |

A를 바탕으로 맞는 행을 지키는 쪽(B의 목표)을 옮겼다.

- 흐름은 A다. 한 소유자의 앱에 대기 테이블·만료·지문·"바뀌었음" 반복과 같은 SQL의 두 번째 예행은 값을 하지 못한다. 서버는 화면의 검사를 믿지 않고 같은 바이트를 다시 읽는다.
- 상품은 링크 판별 값, 컬렉션은 이름(대소문자 무시)으로 맞춘다. 같은 프로젝트에서 실수를 되돌리면 사진과 id가 그대로 남고, 새 프로젝트에서는 파일의 이름·가격을 받은 뒤 사진을 다시 수집한다. 맞은 행의 revision은 오르기만 하므로 오래된 탭이 같은 revision으로 덮어쓰지 못한다(A가 걱정한 ABA). B의 대기 테이블과 revision 하한은 쓰지 않는다.
- A의 `epoch`와 "보이는 상품이 하나도 없는 poll은 전체 읽기로 본다" 규칙은 뺐다. 맞추기 덕분에 늦은 poll은 낮은 revision이거나 모르는 id라 기존 규칙으로 걸러진다.
- 오류 코드와 응답 뒤 작업은 A를 따른다.

두 후보는 같은 모델 계열에서 독립적으로 작성했고 조정자가 합쳤다. 다른 계열 심사는 제공되지 않아 생략했다.

구현은 합친 설계를 따랐고 다음은 설계 문서와 다르다.

- 맞은 상품은 링크 원문(`source_url`)과 쇼핑몰도 파일 값으로 받는다. 판별 값이 같으면 쇼핑몰은 같고, 링크 원문까지 파일과 같아야 "보이는 값이 파일과 같다"가 성립한다.
- 복원 명령(`toLibraryRestoreCommand`)은 4단계가 아니라 3단계에서 만들었다. persistence 검사가 저장소 어댑터의 `restoreLibrary`를 쓰기 때문이다.
- 응답 뒤 작업은 `_server/context.ts` 안이 아니라 `library/application/restore-follow-up.ts`의 `followUpRestore`에 두고 조립 위치는 `after()`로 부르기만 한다. service 검사가 실제 Storage·DB로 같은 함수를 실행한다. 40초 창은 응답 뒤 작업이 시작한 때부터 잰다.
- 읽기 함수는 시각을 밀리초 세 자리로만 받고(정리된 값만 받는 규칙), 모르는 칸이면 위치에 그 칸 이름을 붙인다.
- 내려받기 링크의 주소는 효과(effect)가 만들고 지운다. 같은 효과가 만들고 지우므로 개발 모드의 다시 마운트에서도 지운 주소를 쓰지 않는다. 링크에 초점을 준다.
- 성공 알림은 "새 상품의 사진은"이라고 쓴다. 맞은 상품은 사진을 지키기 때문이다.

- 큰 복원(로컬 native 스택, Apple Silicon macOS). 메모 1,000자와 컬렉션 3개를 가진 상품 1,000개는 0.3~0.8초, 상품 5,000개는 1.1~1.6초(메모 1,000자일 때 RPC 본문 14MB)였다. 로컬 `authenticated`의 문 시간 제한은 8초다. 원 자료는 [restore-timing.txt](../evidence/backup/restore-timing.txt)에 있다. 4MiB 파일은 RPC 본문으로 대략 두 배가 된다(판별 주소와 snake_case 키). 호스팅 Supabase의 시간 제한과 게이트웨이 본문 한도는 확인하지 않았다.
- 실제 스택 브라우저 세 흐름을 두 기기에서 실행한다. 내려받은 파일로 바뀐 보관함을 되돌리고 수집 실패·새로고침·새 세션 뒤에도 파일의 값이 남는다. 바뀐 파일·백업이 아닌 파일·서버가 거절한 파일은 오류를 보이고 아무것도 바꾸지 않는다. 행 잠금으로 복원을 붙잡은 동안 Esc와 닫기가 대화상자를 닫지 못하고, 맞은 상품은 id를 지키며 파일의 메모로 돌아간다. 확인 단계와 오류 단계의 axe 검사, 버튼의 중립 색 검사를 포함한다.

- PC와 iPhone 크기에서 메뉴·내려받기·확인·오류·바꾸는 중·복원 뒤 화면을 캡처해 읽었다. 확인 단계의 개수가 브라우저 기본 `dd` 들여쓰기로 밀려 iPhone에서 줄바꿈되어 고쳤다(`f74c2b0`). 흰색·중립 회색·차콜만 쓰고 오류 문구만 빨간색이며 키보드 초점이 보인다. 캡처용 검사는 커밋하지 않았다.

각 단계의 Red는 `docs/evidence/backup/red-*.txt`에 있다.

- `red-format.txt`: 읽기 함수·파일 만들기·파일 이름이 없을 때 52개 모두 실패한다.
- `red-export-persistence.txt`: `moti_backup`이 없어 내보내기 persistence 3개와 공개 RPC 목록 검사 1개가 실패한다(다른 검사는 이름 필터로 건너뛰었다).
- `red-export-handlers.txt`: `getBackup`과 문서 경로가 없을 때 7개가 실패한다.
- `red-export-http.txt`: 경로 파일을 빼고 빌드했을 때 실제 HTTP 2개가 404로 실패한다.
- `red-restore-command.txt`: 복원 명령이 없을 때 4개가 실패한다.
- `red-restore-persistence.txt`: `moti_restore_library`가 없어 persistence 16개와 공개 RPC 목록 검사 1개가 실패한다.
- `red-restore-handlers.txt`: 복원 처리기·문서 경로·`runWithin`·`followUpRestore`가 없을 때 27개가 실패한다.
- `red-restore-http.txt`: 경로 파일을 빼고 빌드했을 때 실제 HTTP 5개가 404로 실패한다.
- `red-screen.txt`: 대화상자 전환·요청 실행·두 API 클라이언트가 없을 때 58개가 실패한다.
- service 검사(`tests/service/library-backup.test.ts`)는 동작을 만든 뒤 작성해 별도 Red가 없다. 첫 실행의 2개 실패는 고정 페이지의 수집 이름("무선 헤드폰 블랙")을 잘못 적은 테스트 오류였다.
- 실제 스택 브라우저 검사(`tests/browser/library-backup.spec.ts`)도 화면을 만든 뒤 작성해 별도 Red가 없다. 첫 실행에서 두 기기 모두 통과했다.

## 검토

이 기록은 구현 담당자가 썼다. 독립 검토는 아직 없고 조정자가 PR #12에서 한다.

## 남은 범위

- 4MiB를 넘는 보관함은 내려받을 수 있지만 한 번에 복원할 수 없다(일반 상품으로 7,000~10,000개, 모든 칸이 최대인 상품으로 약 115개). 내보내기는 스트리밍하지 않으므로 호스팅의 4.5MB 응답 한도를 넘는 보관함은 내려받기도 실패할 수 있다. 압축 전송이나 나눠 보내기는 하지 않았다.
- 복원 뒤 다시 수집이 성공하면 수집한 이름과 마지막 확인 가격이 새 값으로 바뀐다. 다른 수집과 같다. 소유자 이름·메모·소속·구매는 수집이 건드리지 않고, 실패한 수집은 복원한 값을 지킨다.
- 응답 뒤 약 40초 동안만 수집을 시작한다. 나머지는 멈춤으로 보이고 "다시 가져오기"나 5단위가 처리한다.
- 컬렉션 이름을 바꾼 뒤 이전 백업을 복원하면 이름이 달라 다른 컬렉션으로 보고 지운 뒤 새로 만든다(id가 바뀐다). 소속은 파일대로 다시 만든다.
- 복원 중 다른 기기에서 저장한 링크는 복원이 끝난 뒤 커밋되면 소속 없이 남을 수 있다. 같은 링크를 동시에 저장하면 교착으로 한쪽이 503이 될 수 있다.
- 복원은 소유자의 행 전체를 최대 5초 기다리며 잠근다. 호스팅 Supabase의 `authenticated` 문 시간 제한은 확인하지 않았다(로컬 8초).
- 서명이 없어 구조가 맞는 손 편집은 복원된다.
- 지운 상품을 수집하던 실행이 업로드한 뒤 죽은 경우 등 남는 사본은 5단위의 정리가 지운다(사진 단위와 같다).
- 파일 선택 뒤 4MiB 읽기·검사는 화면의 주 스레드에서 실행한다. 느린 휴대폰에서는 잠시 멈출 수 있다.
- JS `toLowerCase`와 PostgreSQL `lower()`가 드문 글자에서 다를 수 있다. 이때는 DB가 거절하고(400) 아무것도 바뀌지 않는다.
- 실제 Google OAuth, 실제 iPhone의 내려받기와 파일 선택, Vercel(응답 한도, `after()`와 `maxDuration` 60초)과 실제 Supabase 프로젝트는 검증하지 않았다. 브라우저 검사는 로컬 Auth 세션과 iPhone 크기 WebKit이다. 배포는 별도 승인이다.
