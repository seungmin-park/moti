# 내가 살 가격 (소유자가 적는 위시 가격)

소유자가 위시 상품마다 "내가 살 가격"을 직접 적고, 카드와 상세가 그 가격을 주 가격으로 보이게 하는 단위다. 자동으로 확인한 가격은 지우지 않고 참고로 함께 보인다. 지우면 자동 확인 가격으로 돌아간다.

## 왜

자동 확인 가격이 소유자가 실제로 낼 가격이 아닐 때가 있다.

- 네이버 스마트스토어의 키보드 스위치 페이지는 기본 옵션을 "10개 / 3,000원"으로 보여준다. 그런데 페이지의 구조화 데이터는 개당 기준가 300원을 준다. 그래서 moti가 ₩300을 보였다. 수집은 페이지가 하나로 분명히 말하는 가격만 쓰고([metadata.md](metadata.md)), 옵션은 소유자가 적는 글이라 페이지에 물을 수 없다([price-check.md](price-check.md)).
- 옵션 추가금, 묶음, 쿠폰도 같은 문제다.
- 쿠팡·G마켓처럼 읽기를 막는 쇼핑몰은 앱 공유로 담으면 가격이 아예 없다.

가장 작은 변경으로 소유자가 적은 가격(금액과 통화, 원화)을 상품에 두었다. 화면은 이 가격을 수집 가격 대신 보이고, 수집 가격은 "자동 확인 가격 ₩300 · 마지막 확인 …"으로 남긴다. 지울 수도 있다.

## 바뀐 동작

- 마이그레이션 `20261123000000_owner_price.sql`
  - 상품에 `wish_amount_minor bigint`와 `wish_currency text`가 생겼다. 둘 다 null이거나 둘 다 있어야 한다. 금액은 0 이상 2^53−1 이하, 통화는 `KRW`만 받는다. 구매 기록의 실구매가와 같은 규칙이다. 검사는 함수를 부르지 않는 인라인 검사라서 상품을 넣는 역할(`moti_share`)에 새 권한이 필요 없다.
  - `moti.product_json`이 두 열을 함께 보낸다.
  - 새 RPC `public.moti_set_wish_price(p_product_id, p_revision, p_amount_minor, p_currency)`. 금액과 통화가 모두 null이면 지운다. 정리 RPC와 같은 틀이다. `moti_rpc` 소유의 보안 정의자이고 `set search_path = ''`, `moti.require_owner()`를 거치며, `authenticated`만 실행한다(`public`·`anon`·`service_role`은 권한 없음).
    - 검사 순서는 입력(`M0002`) → 대상 없음(`M0006`) → 같은 값 → 오래된 revision(`M0008`) → 상태다. 같은 값이면 revision과 상관없이 지금 상품을 돌려준다.
    - 지금 revision으로 구매완료 상품에 보내면 `M0002`다. 위시 상품의 구매 기록과 같은 판단이다.
    - 값을 바꾸면 revision이 1 오르고 `updated_at`이 바뀐다.
  - `moti_edit_product`는 넓히지 않았다. 인자를 더하면 PostgREST가 함수를 이름과 인자 이름으로 찾으므로 서명이 바뀐다. 그러면 마이그레이션을 배포보다 먼저 적용할 때 이전 앱의 호출이 깨지거나 같은 이름의 함수가 두 개 남는다. 가격 저장은 이름·메모 저장과 다른 양식이기도 하다.
  - `moti.backup_json`이 두 열을 함께 내보낸다. `public.moti_restore_library`는 서명·소유자·권한을 그대로 두고 본문만 바꿨다. 먼저 기존 `moti.restore_library`가 보관함을 바꾼다. 같은 트랜잭션에서 새 `moti.restore_wish_prices`가 파일의 가격을 검사하고 링크 판별 값이 맞는 상품에 쓴다. 그 뒤 보관함을 다시 읽어 돌려준다. 가격이 잘못되었으면 `M0002`이고 복원 전체가 되돌아간다. 가격이 없는 입력(이전 앱)은 모든 상품을 가격 없이 복원한다.
- 수집과 가격 확인
  - 수집(소유자의 수집·"다시 가져오기"·예약 수집)과 매일 가격 확인은 지금처럼 `last_success_*`만 쓴다. 아무 SQL도 바꾸지 않았다. 작업 역할 `moti_worker`는 새 열에 권한이 없다. 권한 목록을 고정한 catalog 검사가 그대로 통과한다.
  - 매일 가격 확인의 이유(`price_check_code`)도 자동 확인 가격에 대한 것이다. 소유자 가격이 있는 상품의 상세는 "{서울 날짜}에 가격을 다시 확인하지 못해 자동 확인 가격은 이전에 확인한 가격이에요. {이유}"라고 말한다. 소유자 가격이 없으면 이전 문구("이전 가격을 보여줘요.")다. 줄을 보이는 조건은 그대로다.
- 구매
  - 구매완료로 옮겨도 소유자 가격은 그대로 남고 화면에서만 숨는다. 실구매가로 옮겨 적지 않는다. 구매 전환은 지금처럼 구매일·실구매가를 비운다.
  - 실구매가는 "실제로 낸 값"이고 빈 값과 0원이 다르다. 미리 채우면 적지 않은 값이 기록된다. 실행 취소의 "구매 전으로 되돌리기"도 정확해야 한다.
  - 위시로 되돌리면 소유자 가격이 다시 보인다. 구매완료 카드와 상세의 가격은 지금과 같다(실구매가, 상세는 마지막 확인 가격).
- 백업 파일(`moti.library-backup` 버전 1)
  - 소유자 가격이 있는 상품에만 선택 칸 `wishPrice: { amountMinor, currency: "KRW" }`가 붙는다.
  - 읽기 함수는 모르는 칸을 거절하는 엄격한 함수다. 그래서 칸을 늘 쓰면 이전 앱이 새 파일을 모두 거절한다. 가격이 없는 보관함은 이전과 같은 파일을 만들고, 이전 앱도 읽는다. 가격이 있는 파일은 이전 앱에서 `products.N.wishPrice`의 손상된 파일로 거절된다.
  - 버전 2로 올리지 않았다. 이전 앱의 안내("더 새로운 moti")가 더 친절하지만 모든 새 파일을 이전 앱이 거절하게 된다. 앱과 서버는 함께 배포되므로 이 차이는 배포 직후의 열린 탭에만 해당한다.
  - `wishPrice: null`은 앱이 쓰지 않는 값이라 거절한다.
  - 이전 파일(칸 없음)은 그대로 읽고, 복원하면 링크가 맞은 상품도 소유자 가격이 없어진다. 복원은 소유자 값을 파일로 바꾸는 동작이고, 소유자 이름·메모와 같다.
- HTTP
  - 새 경로 없이 `PATCH /api/products/{productId}`에 `change.type: "wish.price"`를 더했다. 본문은 `{ "revision": 3, "change": { "type": "wish.price", "price": { "amountMinor": 3000, "currency": "KRW" } } }`이고, 지우기는 `"price": null`이다. zod는 모양만 검사하고 모르는 칸을 거절한다.
  - 명령(`toProductChangeCommand`)은 실구매가와 같은 규칙으로 검사한다. 어기면 400 `invalid_input`, `field: "wishPrice"`, "내가 살 가격은 0 이상의 정수로 입력해 주세요."다.
  - 응답의 `ProductResponse`에 `wishPrice: { amountMinor, currency } | null`이 생겼다. 상태 코드는 기존 PATCH와 같다. 200, 400, 401, 403, 404 `product_missing`, 409 `revision_conflict`, 413, 415, 503이다.
  - `docs/api/openapi.json`을 다시 생성했다. 보관함 읽기·저장·다시 가져오기·깨우기·복원 응답이 같은 상품 스키마를 쓴다.
- 화면
  - 규칙은 순수 모듈 `wishlist/product-fields.ts`의 `parseWishPrice`와 `wishPriceInput`이다. "3000"과 "3,000"을 모두 받고, 빈 칸은 지우기이며 0원과 다르다. 저장한 값은 "3,000"처럼 묶어 보인다.
  - 위시 상품의 상세에 "내가 살 가격 원" 칸을 두었다. 숫자 키패드(`inputMode="numeric"`)와 도움말("옵션·묶음·쿠폰으로 실제 낼 가격이 다르면 적어 주세요. 자동 확인 가격은 따로 남아요.", `aria-describedby`)이 있다.
  - "가격 저장"은 이름·메모 저장과 따로 있는 작은 양식이다. 금액이 바뀌었을 때만 켜지고, 쉼표만 다른 값은 바뀐 것이 아니다. Enter로도 저장한다.
  - 소유자 가격이 있으면 "직접 입력 지우기"가 보인다. 오류는 칸 아래 `role="alert"`와 `aria-invalid`로 보인다. 저장하면 "내가 살 가격을 저장했어요", 지우면 "직접 입력한 가격을 지우고 자동 확인 가격을 보여줘요"다.
  - 카드와 상세는 소유자 가격을 주 가격으로 보이고 옆에 "직접 입력" 표시를 붙인다. 표시는 중립 회색 테두리이고 초록·세이지는 쓰지 않는다. 그 아래에 자동 확인 가격을 둔다.
    - 카드: "자동 확인 ₩300"
    - 상세: "자동 확인 가격 ₩300 · 마지막 확인 2026. 11. 11."
    - 자동 확인 가격이 없으면 "자동 확인 가격 없음"
  - 화면 전환은 기존 상세 양식과 같다. 손댄 칸만 초안에 두고, 쓰기는 한 번에 하나다. 409는 다시 읽고 초안을 지킨다. 응답과 다시 읽기는 revision으로 합친다. 수집 진행만 합치는 주기적 다시 읽기는 소유자 가격을 건드리지 않는다.
  - `/demo` 목업은 바꾸지 않았다. 목업 계약에 이 기능이 없다.

## 설계 선택

| 기준 | 고른 것 | 다른 길 |
| --- | --- | --- |
| 저장 | 상품의 두 열(`wish_*`), 수집 열과 분리 | 마지막 확인 가격을 덮어쓰기. 다음 수집이 지우고 참고 가격이 사라진다 |
| RPC | 새 `moti_set_wish_price` | `moti_edit_product`에 인자 추가. 이전 앱의 호출과 서명이 어긋난다 |
| HTTP | 기존 PATCH의 새 `change.type` | 새 경로. 같은 자원의 두 번째 쓰기 경로와 오류 대응표가 생긴다 |
| 이름 | `wishPrice`(화면 "내가 살 가격") | `ownerPrice`. 구매완료의 실구매가와 함께 보면 위시의 가격이라는 뜻이 더 분명하다 |
| 구매 | 남기고 숨김, 실구매가로 옮기지 않음 | 실구매가로 미리 채우기. 적지 않은 값이 실제 기록이 된다 |
| 백업 | 버전 1의 선택 칸, 값이 있을 때만 | 버전 2. 이전 앱이 모든 새 파일을 거절한다 |
| 복원 | 래퍼 함수 안에서 같은 트랜잭션으로 가격만 덧쓰기 | `moti.restore_library` 전체를 다시 정의. 140줄을 복사해 고친다 |

`feat/owner-price`(`main` bccc3e9에서 시작)에서 로컬 `npm run verify`(종료 0)로 개수를 확인했다. PR과 CI는 아직 없다.

- 단위: 규칙(쉼표 묶음, 빈 칸과 0원, 거절할 값 9가지, 입력 칸 표시), 명령(원화 금액·지우기·잘못된 금액 4가지), 백업(값이 있을 때만 칸, 왕복, 이전 버전 1 파일, 잘못된 칸 5가지), 처리기 Given–When–Then(저장·지우기 200, 모양 오류 3가지와 규칙 오류 3가지의 400과 `field`, 응답의 두 가격), 화면(카드·상세 문구, 막힌 쇼핑몰, 0원, 구매완료, 이전 가격 줄 문구, 저장·지우기·같은 값·오류·충돌·성공 알림, 수집 진행 합치기), API 클라이언트의 `wishPrice` 칸 오류, OpenAPI 일치.
- persistence: 저장·지우기·0원, 같은 값, 오래된 revision, 구매완료 상품, 다른 소유자와 없는 상품, 잘못된 입력 7가지, 테이블 제약, 익명과 다른 계정을 확인한다. 이어서 수집과 "다시 가져오기"가 소유자 가격을 지키는지, 작업자의 매일 가격 확인이 자동 확인 가격만 바꾸는지 확인한다. 구매·기록·되돌리기, 이름·메모 수정, 내보내기도 확인한다. 복원은 맞은 상품, 새 상품, 칸 없는 이전 파일, 내보낸 파일 왕복, 잘못된 가격 4가지의 `M0002`와 보관함 그대로를 확인한다. 공개 RPC 목록 검사에 새 함수를 더했다.
- service: 실제 수집 실행기(고정 쇼핑몰 페이지 ₩289,000)가 소유자 가격을 지킨다. 지우기, 구매완료 거절, 오래된 revision도 확인한다. 백업 파일 글자를 읽기 함수로 다시 읽어 복원하는 왕복도 확인한다.
- 실제 HTTP: 저장·새 세션 읽기·지우기, 잘못된 가격 3가지의 400 `wishPrice`, 409, 다른 출처 403을 확인한다. 백업 파일에 가격이 담기는지, 칸을 뺀 이전 파일로 복원하면 가격이 없어지는지, 받은 파일로 다시 복원하면 돌아오는지도 확인한다.
- 실제 스택 브라우저는 두 기기에서 두 흐름을 확인한다.
  - ₩300 상품에 "30,00"을 넣으면 칸 오류와 `aria-invalid`가 보이고 DB는 그대로다. "3,000"을 저장하면 상세·카드에 ₩3,000과 "직접 입력", 자동 확인 가격 ₩300이 보인다. 표시의 중립 색, axe 위반 0, 가로 넘침 없음, 새로고침과 새 세션의 유지도 확인한다.
  - "직접 입력 지우기"로 ₩300으로 돌아간다. 키보드로 "2900" 입력과 Enter 저장을 하면 "2,900"으로 보인다.

Red는 [docs/evidence/owner-price/red.txt](../evidence/owner-price/red.txt)에 있다.

- 단위: 테스트만 바꾼 상태에서 66개가 실패했다(`parseWishPrice is not a function`, 명령·읽기 함수의 `wishPrice` 없음). 처리기와 API 클라이언트의 기존 검사 일부도 실패했다. 고정값에 `wishPrice: null`을 더했는데 엄격한 응답 계약에 그 칸이 아직 없기 때문이다.
- persistence: 마이그레이션 없이 새 검사 26개와 공개 RPC 목록 검사가 실패했다(`PGRST202` 함수 없음, `wish_amount_minor` 열 없음). 같은 파일의 나머지 보안 검사 18개는 통과했다.
- service·HTTP·브라우저 검사는 마이그레이션과 계약을 만든 뒤 작성해 따로 Red를 보지 않았다.

첫 DB 실행에서 두 검사가 실패했고, 둘 다 테스트를 고쳤다.

- 기존 `library-backup.test.ts`의 내보내기 기대값에 `wishPrice: null`이 없었다. 저장소의 `BackupProduct`가 늘 그 칸을 갖게 되어 기대값을 고쳤다.
- 새 검사가 다시 가져오기를 준비하려고 상품을 `failed`로 바꾸면서 사진 결과를 남겨 테이블 제약에 걸렸다. 사진만 실패한 상품("다시 가져오기"가 보이는 다른 경우)으로 준비를 바꿨다.

## 남은 범위

- 원화만 받는다. 실구매가와 같은 한계다. 자동 확인 가격이 다른 통화여도 소유자 가격은 원화다.
- 소유자 가격은 위시 상품의 상세에서만 고친다. 카드에서 바로 고치는 칸은 없다.
- 가격 정렬·합계는 실제 화면에 아직 없다. 생기면 소유자 가격을 먼저 쓸지 정해야 한다.
- 가격이 있는 백업 파일은 배포 전 앱의 열린 탭에서 "손상된 파일"로 거절된다. 새로고침하면 읽는다.
- 구매완료 상품의 숨은 소유자 가격은 화면에서 볼 수도 지울 수도 없다. 위시로 되돌리면 보이고 고칠 수 있다. 복원 파일에는 남는다.
- 실제 스마트스토어 페이지, 실제 iPhone, 운영 Supabase, 호스팅은 검증하지 않았다. 마이그레이션은 로컬 native 스택에만 적용했다. 배포는 별도 승인이다.
