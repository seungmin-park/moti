# 상세에서 새 컬렉션 만들기

소유자가 실제 보관함(`/`)의 상품 상세("담아둔 물건")에서 바로 새 컬렉션을 만드는 단위다. 지금까지 상세의 컬렉션 칸은 이미 있는 컬렉션 체크만 할 수 있었다. 새 컬렉션에 담으려면 상세를 닫고 사이드바의 "내 컬렉션 +"로 만든 뒤 상세를 다시 열어야 했다. 가장 작은 변경으로 체크 목록 아래에 "새 컬렉션" 버튼과 이름 칸을 두었다. 만들기는 기존 `POST /api/collections`(`moti_create_collection`)를 그대로 쓴다. 마이그레이션, API 계약, OpenAPI 문서는 바뀌지 않았다.

## 바뀐 동작

- 상세의 컬렉션 체크 목록 아래에 "+ 새 컬렉션"(텍스트 버튼)이 있다. 누르면 그 자리에 "새 컬렉션 이름" 칸과 "만들기"·"취소"가 열리고 초점이 이름 칸으로 간다.
- Enter나 "만들기"를 누르면 컬렉션을 만든다. 만드는 동안 버튼은 "만드는 중…"이 된다. 이름 칸·"변경사항 저장"·닫기·다른 상세 쓰기는 기다린다. 성공하면 이름 칸이 닫히고 새 컬렉션이 목록 끝에 체크된 채 나타나며 초점이 그 체크 상자로 간다. 사이드바(모바일은 칩)의 컬렉션 목록에도 새로고침 없이 개수 0으로 나타난다.
- 새 컬렉션은 상세의 초안(손댄 칸 초안 `draft.collectionIds`)에만 더해진다. 이미 고친 이름·메모·체크는 그대로 남는다. 상품의 소속은 "변경사항 저장"을 눌러야 저장되고, 그때 사이드바 개수가 1이 된다. 기존 저장·충돌(409) 처리와 같다. 거절되면 최신 내용을 다시 읽고 고친 칸과 새 체크를 지킨다.
- Esc나 "취소"는 이름 칸만 닫는다. 상세는 열린 채이고 초점은 "+ 새 컬렉션"으로 돌아간다. 이름 칸 안의 Enter·Esc는 상세 양식을 제출하거나 상세를 닫지 않는다. 한글 조합 중의 Enter·Esc(`isComposing`, keyCode 229)는 무시한다.
- 검사와 문구는 "새로운 컬렉션" 대화상자와 같다. 빈 이름과 41자 이상은 "컬렉션 이름은 1~40자로 입력해 주세요.", 대소문자·앞뒤 공백·정규화만 다른 이름은 "같은 이름의 컬렉션이 이미 있어요."이다. 이 경우 요청하지 않는다. 오류는 이름 칸 아래에 `role="alert"`로 보이고 칸은 `aria-invalid`이다. 이름을 고치면 오류가 사라진다. 다른 곳에서 같은 이름을 먼저 만들어 서버가 거절하면(409 `collection_duplicate`) 같은 문구를 보이고 보관함을 다시 읽는다. 일시적 실패는 이름을 지키고 안내한다. 세션이 끝났으면 로그인으로 간다. 다시 읽는 중에는 만들지 않는다.
- 만든 뒤 저장하지 않고 상세를 닫으면 빈 컬렉션이 남는다. 컬렉션 만들기는 그 자체로 저장되는 동작이고, 사이드바에서 만든 컬렉션과 같다. 컬렉션 삭제는 아직 없다.
- 색은 흰색·중립 회색·차콜이다. 이름 칸의 초점은 기존 입력과 같은 중립 배경과 하단 강조, 버튼의 키보드 초점 표시는 기존 규칙 그대로다. 오류 문구만 오류 색이다.
- `/demo` 목업은 바뀌지 않았다. 목업 계약은 상세의 컬렉션 수정만 요구하고, 목업의 링크 추가 창에는 이미 검색·만들기 선택 창(`CollectionPicker`)이 있다.

## 설계 선택

- 링크 추가 창의 `CollectionPicker`를 다시 쓰지 않았다. 그 창은 검색하고 고르는 드롭다운이고, 이미 있는 이름을 적으면 오류 대신 그 컬렉션을 고른다. 상세의 컬렉션 칸은 모든 컬렉션을 체크 목록으로 이미 보여주므로 드롭다운이 필요 없다. 그래서 요청대로 "새로운 컬렉션" 대화상자와 같은 검사·문구를 쓰는 이름 칸 하나를 더했다. 이름 규칙(`wishlist/collection-name.ts`)과 같은 이름 검사(`sameName`), 실패 처리(`failForm`)는 그대로 함께 쓴다.
- 화면 상태: 상세 대화상자에 선택 칸 `newCollection: { name, creating }`을 더하고 사건 넷(`detail.collectionOpen`·`Edit`·`Cancel`·`Create`)을 더했다. 요청은 기존 `collection.create`이고 출처 `from`에 `"detail"`을 더해 결과를 상세로 돌려준다. 오류는 상세의 기존 알림(`DetailNotice`)에 새 양식 이름 `"collection"`으로 담는다. 만드는 중은 `busy`로 묶어 닫기와 다른 상세 사건을 막는다. 링크 추가 창의 만들기와 같다.
- 성공한 컬렉션은 초안에만 체크한다. 소속을 바로 저장하면 한 동작이 두 쓰기(컬렉션, 상품 revision)가 되고, 고친 이름·메모가 있는 초안과 섞여 충돌 처리가 복잡해진다. 상세의 "변경사항 저장"이 소속을 쓰는 유일한 경로로 남는다.
- 초점은 화면 상태가 아니라 컴포넌트가 정한다. 이름 칸이 열릴 때의 컬렉션 id를 기억해 두고, 닫힐 때 새로 생겨 체크된 컬렉션이 있으면 그 체크 상자, 없으면 "+ 새 컬렉션"으로 옮긴다. 그사이 소유자가 다른 입력 칸으로 옮겼으면 옮기지 않는다.

`main`(952933a)에서 시작한 `feat/detail-collection`의 로컬 `npm run verify`(종료 0)로 개수를 확인했다. 서버 쪽 코드가 바뀌지 않아 실제 DB·HTTP 검사는 늘지 않았다. 만들기 요청은 기존 HTTP 검사(`POST /api/collections`)와 이번 브라우저 검사가 실제 스택에서 확인한다.

- 화면 상태 단위(`screen-state.test.ts`의 "상세에서 새 컬렉션 만들기", 11개): 열기·이름 적기·취소(저장 알림을 지우고 요청 없음), 정리한 이름으로 `from: "detail"` 요청과 만드는 중의 다시 만들기·취소·이름 고치기·체크·저장·닫기 무시, 빈 이름·41자·대소문자만 다른 이름의 문구와 이름을 고치면 오류가 사라짐, 성공하면 목록 끝에 더하고 이름 칸을 닫으며 다른 초안과 함께 체크하고 저장 요청은 하지 않음(이어서 저장하면 새 컬렉션까지 보냄), 기존 체크를 뺀 초안을 지킴, 일시적 실패, 서버의 이름 중복(다시 읽기, 다시 읽는 중 만들기 무시, 다시 읽은 뒤 같은 이름 거절), 세션 만료, 상품 저장 중 무시.
- 실제 스택 브라우저(`tests/browser/detail-collection.spec.ts`, 3개 × 두 기기): 키보드로 "새 컬렉션" 열기(초점이 이름 칸, 중립 초점 색, 열린 상세의 axe 위반 0), Enter로 만들기(체크되고 초점이 새 체크 상자, 기존 체크 유지, 사이드바·칩 개수 0, DB에 빈 컬렉션), "변경사항 저장" 뒤 개수 1과 DB 소속, 새로고침 뒤 체크 유지. Esc는 이름 칸만 닫고 초점이 "새 컬렉션"으로 돌아오며 아무것도 만들지 않음, "만들기"로 만든 뒤 저장하지 않고 닫으면 빈 컬렉션만 남음. 빈 이름과 이미 있는 이름(앞뒤 공백·대소문자)은 오류를 보이고 `aria-invalid`, "변경사항 저장"은 꺼진 채이고 DB는 그대로.

Red는 `docs/evidence/detail-collection/red.txt`에 있다.

## 남은 범위

- 만든 뒤 저장하지 않고 닫으면 빈 컬렉션이 남는다. 지우는 방법(컬렉션 삭제)은 아직 없다.
- 구매완료 상품의 상세에도 같은 칸이 있다(기존 컬렉션 체크가 구매 상태와 무관하게 있으므로).
- 실제 iPhone의 키보드·한글 입력기, 실제 Google OAuth, 운영 Supabase와 호스팅에서는 확인하지 않았다. 브라우저 검사는 로컬 Auth 세션과 iPhone 크기 WebKit이다. 배포는 별도 승인이다.
