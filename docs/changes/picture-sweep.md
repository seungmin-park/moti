# 남은 사진 정리 (5c)

어떤 상품도 쓰지 않는 비공개 사진 사본을 소유자가 moti를 열 때 지우는 단위다. 이전에는 이런 사본이 Storage에 계속 남았다. 3b에서 업로드한 뒤 죽은 실행, 예외를 던진 정산, 서명 업로드 주소로 쓴 객체가 남겼고, 4b에서 복원 뒤 실패한 지우기가 남겼다. 예약 실행(5a)은 Storage에 닿지 못한다. Storage는 소유자의 JWT로만 권한을 정하기 때문이다. 그래서 정리는 소유자의 화면이 이미 부르는 깨우기(`POST /api/library/metadata`)의 응답 뒤에 돈다. 화면에 보이는 사본, 끝나지 않은 작업이 아직 기록할 수 있는 사본, 만든 지 10분이 안 된 사본은 지우지 않는다. 소유자에게 보이는 변화는 "자동 확인"의 안내 한 줄이다.

5단위를 나눈 세 번째이자 마지막 PR이다. 5a는 정기 수집, 5b는 매일 가격 확인이다.

## 바뀐 동작

- 마이그레이션 `20261119000000_picture_sweep.sql` 하나에 이 단위의 SQL이 있다. 병합한 마이그레이션은 고치지 않았다.
  - `moti.stored_pictures(p_owner, p_before)`는 `product-pictures` 버킷에서 `<소유자 id>/`로 시작하고 `p_before`보다 먼저 만든 객체의 이름만 돌려준다. `moti_rpc`는 `storage` 스키마를 읽지 못하므로 `stored_picture_version`처럼 마이그레이션 소유자의 권한으로 실행한다(보안 정의자). 실행할 수 있는 역할은 `moti_rpc`뿐이다. 한도는 없다.
  - 새 소유자 RPC `public.moti_picture_orphans(p_limit)`는 `moti_rpc`가 소유하고 다른 소유자 RPC와 같이 `moti.require_owner()`로 시작한다. 소유자가 아닌 세션은 `M0001`, 익명은 실행 권한이 없어 `42501`이다. 한도는 1 ~ 200이고 아니면 `M0002`다. 답은 이름의 JSON 배열(이름 순)이고 다음을 모두 만족하는 이름만 담는다.
    - 부른 소유자의 접두사 아래에 있고 만든 지 10분이 지났다.
    - 어떤 상품도 그 이름을 지금 사본으로 쓰지 않는다.
    - 수집 중(`running`)인 작업의 이번 시도 이름이 아니다.
  - 목록의 두 번째와 세 번째 조건은 `moti_storage.may_discard`의 두 조건과 같은 식이다. 접두사 조건은 `stored_pictures`가 맡는다. `may_discard`에는 나이 조건이 없고, 이 RPC는 10분 여유만큼 더 엄격하다.
- 앱
  - `src/features/library/application/picture-sweep.ts`의 `sweepPictures`는 두 포트(`PictureOrphanStore`, 기존 `PictureStore`)만 쓰는 순수 조립이다. 남은 사본을 200개(`SWEEP_BATCH`)까지 묻고, 받은 이름을 그대로 `discard`에 넘긴다. Storage가 소유자 토큰으로 `may_discard`를 한 번 더 확인한다. 한 번에 한 차례만 하고 다시 묻지 않는다. 예외를 던지지 않고, 결과는 이름 없이 넘긴 개수(`requested`) 또는 예외가 난 단계(`failed`)다.
  - `library/infrastructure/product-pictures.ts`의 `createPictureOrphanStore`가 RPC를 부르고 기존 이름 스키마로 답을 읽는다.
  - 깨우기 처리기는 깨우기가 성공하면 깨운 상품이 있든 없든 `sweep()`을 맡긴다. 거절(다른 출처, 잘못된 본문, 세션 없음)과 저장소 오류에서는 맡기지 않는다. `src/app/_server/context.ts`가 응답 뒤 클라이언트(호출마다 10초)로 `after()`에서 정리를 실행한다. 응답 본문은 그대로다.
  - ESLint가 작업자 폴더와 예약 실행 경로에서 `picture-sweep`도 막는다. 정리는 소유자 경로에만 있다.
  - `docs/api/openapi.json`의 깨우기 설명에 응답 뒤 정리를 적었다. 5a가 빠뜨린 사진 대기 상품의 재대기도 함께 적었다.
- 화면
  - 화면은 보관함을 처음 받을 때마다 깨우기를 부른다. 뒤로 가기 캐시에서 돌아와 다시 읽을 때도 같다. 이전에는 시도 0인 대기 상품이나 사진을 기다리는 상품이 있을 때만 불렀다. 5a가 이 변경을 5c로 미뤘다.
  - "자동 확인"의 마지막 안내가 "사진은 moti를 열 때 가져와요."에서 "사진 복사와 남은 사진 정리는 moti를 열 때 해요."로 바뀌었다. 다른 화면은 그대로다.

## 설계 선택

큰 선택은 5a·5b와 함께 정했다(계약 `5-design.md`, 후보 A). 정리는 소유자의 깨우기에서 돌고, SQL이 이름만 돌려주며, Storage의 지우기 정책이 다시 확인한다. 구현하며 정한 것은 아래와 같다.

| 기준 | 고른 것 | 다른 길 |
| --- | --- | --- |
| 한도를 세는 곳 | 참조 검사 뒤 | `stored_pictures` 안. 상품이 쓰는 사본은 지워지지 않고 가장 오래돼 한도를 채운다 |
| 조건의 표현 | `may_discard`의 두 조건을 한 번의 anti-join으로 | 이름마다 `may_discard` 호출. 이름마다 상품 전체를 다시 읽는다 |
| 한 번에 지우는 양 | 열 때마다 한 차례, 200개 | 다 지울 때까지 반복. Storage가 거절한 이름이 같은 답으로 돌아와 기한까지 돈다 |
| 깨우기를 부르는 때 | 모든 첫 로드 | 깨울 상품이 있을 때만. 그러면 정리가 거의 돌지 않는다 |

이름마다 `may_discard`를 부르는 첫 구현은 같은 식을 두 번 쓰지 않아도 되지만 상품 수의 제곱으로 느려졌다. 로컬 스택의 pg 연결에서 한 트랜잭션에 상품과 객체 행을 만들고 소유자 세션으로 RPC 함수의 시간을 잰 뒤 되돌렸다(상품마다 보이는 사본 하나, 남은 사본 50개, 크기마다 한 번). PostgREST와 네트워크 시간은 빠져 있다. 상품 300·1,000·3,000개에서 183 ms·1.4초·11.2초였고, anti-join은 3.1 ms·6.6 ms·17.4 ms, 10,000개에서 55 ms였다. 3,000개면 응답 뒤 클라이언트의 10초 제한을 넘는다. 두 표현이 같은 답을 내는지는 persistence 검사가 Storage의 실제 지우기와 비교해 고정한다.

한 차례는 RPC 하나와 Storage 지우기 하나다. 둘 다 10초 제한이라 최악 20초이고 깨우기의 수집 창(`WAKE_WINDOW_MS`, 40초) 안이다. 정리는 수집과 따로 `after()`로 돌아 수집을 늦추지 않는다. 쌓인 사본이 200개를 넘으면 열 때마다 200개씩 줄어든다.

### 설계와 다르게 구현한 것

- `moti.stored_pictures`에 한도가 없다. 계약은 `stored_pictures(prefix, before, limit)`였다. 한도를 여기서 세면 상품이 쓰는 오래된 사본이 답을 채워 그 뒤의 남은 사본을 영영 찾지 못한다(`red-sql-defects.txt`의 2번). RPC가 참조 검사 뒤에 한도를 센다.
- 접두사 대신 소유자 id(`uuid`)를 받는다. 함수가 `<id>/`를 만들어 다른 경로나 패턴을 넘길 수 없다.
- RPC는 `may_discard`를 부르지 않고 같은 두 조건을 anti-join으로 쓴다. 위의 측정 때문이다. 결과는 `may_discard`와 같고 나이만큼 더 엄격하다. 이 검사가 같은 식을 지키는지는 persistence 검사(돌려준 사본만 소유자의 Storage 지우기로 지워진다)가 확인한다.
- 화면이 모든 첫 로드에 깨운다. 계약에 있던 변경인데 5a가 미뤘다. 조정자의 지시는 화면 변경을 안내 문구만 예상했다. 이 변경이 없으면 정리가 깨울 상품이 있는 열기에서만 돌아 목표를 채우지 못한다.
- 결과 이름이 `requested`다. `PictureStore.discard`는 실패를 삼키고 Storage의 답을 돌려주지 않아 정리가 실제로 지운 개수를 모른다. 넘긴 개수만 말한다.
- 커밋은 넷이다. SQL(`5a9cc73`), 정리와 연결(처리기·조립·어댑터·service·HTTP, `3498221`), 화면(`ac99cac`), 문서다.

- 단위는 정리의 조립(200개를 한 번 묻고 받은 이름 그대로 버리기, 남은 사본이 없으면 Storage를 부르지 않기, 한도만큼 받아도 다시 묻지 않기, 두 포트의 예외를 이름 없는 결과로 바꾸기), 깨우기 처리기(성공하면 깨운 상품이 있든 없든 정리를 맡기고 거절·401·503에서는 맡기지 않기), 화면(사진 대기·사진 있음·수집 중·상품 없음의 첫 로드와 뒤로 가기 캐시 복귀가 모두 깨우기)을 확인한다.
- persistence는 나이(9분과 11분), 상품이 쓰는 사본, 임대가 지나도 끝나지 않은 작업의 이번 시도와 다음 시도가 맡은 뒤, 다른 계정 접두사, 한도가 참조 검사 뒤에 세어지는지(오래된 보이는 사본 둘과 남은 사본 둘, 한도 1·2), 돌려준 사본만 소유자의 Storage 지우기로 지워지는지, 한도 `M0002`, `M0001`·`42501`, 어댑터, `stored_pictures`와 `picture_orphans`의 소유자·보안 정의자 여부·실행 권한(`moti_rpc`만, `anon`·`authenticated`·`moti_worker`는 못 함)과 공개 REST에 드러나지 않음, 공개 함수 목록을 확인한다. 나이는 `storage.objects.created_at`을 되돌려 만든다.
- service는 실제 DB·Storage로 10분 지난 남은 사본만 지우고 보이는 사본·끝나지 않은 작업의 사본·9분 된 남은 사본을 남기는지, 아무도 듣지 않는 주소의 Storage로 지우기가 실패해도 예외 없이 끝나고 다음 정리에서 지우는지 확인한다. `afterEach`가 Storage API로 사진을 먼저 지운다.
- 실제 HTTP는 화면처럼 부른 깨우기가 202와 같은 본문을 돌려주고, 응답 뒤 10초 안에 11분 된 남은 사본이 사라지며 보이는 사본은 남는지 확인한다.
- 실제 스택 브라우저는 깨울 상품이 없는 보관함을 열어도 화면이 깨우기를 보내 202를 받는지, "자동 확인"이 새 안내를 보이는지 두 기기에서 확인한다(기존 검사에 단언을 더했다).
- PC Chromium(1440×900)과 iPhone 크기 WebKit(390×664)에서 자동 확인의 새 안내를 캡처해 읽었다. 두 화면 모두 안내가 한 줄에 들어가고 중립 회색이며 가로로 넘치지 않는다. 캡처용 검사는 커밋하지 않았다.

각 단계의 Red는 `docs/evidence/picture-sweep/red-*.txt`에 있다.

- `red-sql-missing.txt`: 새 마이그레이션이 없어 RPC가 없고(`PGRST202`) 새 persistence 11개와 공개 함수 목록 검사가 실패한다.
- `red-sql-defects.txt`: 결함 넷을 하나씩 넣었을 때 각 규칙을 지키는 검사만 실패한다. 나이 여유 없음, 참조 검사 전에 센 한도, 상품이 쓰는 사본 검사 없음, 끝나지 않은 작업의 사본 검사 없음이다. 권한을 건드리는 결함은 없다.
- `red-sweep-unit.txt`: `sweepPictures`가 같은 서명으로 아무것도 하지 않을 때 4개가 실패한다.
- `red-handler.txt`: 처리기가 정리를 맡기지 않을 때 성공한 깨우기 둘이 실패한다.
- `red-service.txt`: 정리와 어댑터가 같은 서명으로 아무것도 하지 않을 때 어댑터 검사와 service 둘이 실패한다.
- `red-http.txt`: 처리기가 정리를 맡기지 않는 빌드에서 새 HTTP 검사가 실패하고 나머지 45개는 통과한다.
- `red-screen-unit.txt`: 화면이 깨울 상품이 있을 때만 깨울 때 첫 로드 셋과 캐시 복귀 하나가 실패한다.
- `red-browser.txt`: 이전 화면의 빌드에서 바꾼 브라우저 검사가 두 기기 모두 실패하고 나머지 48개는 통과한다. 첫 실행은 새 안내가 없어 실패했지만 깨우기 단언은 잘못된 이유로 통과했다. 준비가 작업의 시도 수만 1로 두고 상품의 시도 수는 0으로 남겨 이전 화면도 깨웠기 때문이다. 준비를 고친 두 번째 실행에서는 이전 화면이 깨우기를 보내지 않아 두 기기 모두 시간 초과로 실패한다.
- 작업자 경계의 ESLint는 작업자 폴더에 `picture-sweep`을 가져오는 임시 파일을 두고 바꾸기 전 통과, 바꾼 뒤 실패를 확인한 뒤 지웠다.
- 기존 검사 중 바꾼 것. 공개 함수 목록(`library-security.test.ts`)에 새 RPC를 더했다. 깨우기 처리기 검사의 맥락에 `sweep`을 더하고 기존 다섯 검사에 정리 여부를 단언했다. 화면에서 깨우지 않는다고 단언하던 검사 둘은 새 동작과 반대라 모든 첫 로드가 깨운다는 검사로 바꿨다. 자동 확인 브라우저 검사의 준비는 작업과 함께 상품의 시도 수도 1로 둔다.

독립 검토는 아직 하지 않았다. 조정자가 이 PR의 head에서 검토와 검증을 따로 실행한다.

## 남은 범위

- 운영 Storage. Storage가 소유자 토큰으로 `may_discard`를 확인하고 `created_at`을 만든 시각으로 두는 동작은 로컬 native 스택에서만 확인했다. 호스팅의 `after()`가 `maxDuration` 60초 안에서 끝까지 도는지도 확인하지 않았다.
- 완료 뒤 서명 업로드 주소로 바뀐 사본은 상품이 여전히 그 이름을 가리켜 남는다. `may_discard`도 거절한다. 3b는 이 사본을 정리가 지운다고 적었지만, 상품이 가리키는 이름을 지우면 보이는 사본을 지우지 않는다는 규칙과 부딪혀 지우지 않는다. 다시 수집해 새 사본이 생기면 기존 지우기 경로가 지운다.
- 업로드한 뒤 죽은 실행의 사본은 다음 시도가 작업을 맡거나 다시 가져오기가 세대를 바꾼 뒤에만 정리 대상이다. 멈춘 채 아무도 다시 가져오지 않는 작업의 사본은 남는다.
- 나이는 `created_at`으로 잰다. 서명 업로드 주소의 덮어쓰기가 `created_at`을 바꾸는지는 확인하지 않았다. 보이는 사본을 지키는 것은 나이가 아니라 참조 조건이라 결과는 같다.
- moti가 만들지 않은 이름(서비스 키나 대시보드로 소유자 접두사에 올린 객체)이 있으면 어댑터가 답 전체를 거절해 그 객체가 사라질 때까지 정리가 아무것도 하지 않는다. 앱의 경로로는 그런 이름을 만들 수 없다.
- 쌓인 사본이 200개를 넘으면 열 때마다 200개씩 줄어든다.
- 열 때마다 깨우기 POST 하나가 늘었다. 깨울 것이 없으면 깨우기 RPC, 남은 사본 RPC 하나씩이고, 남은 사본이 있을 때만 Storage 지우기 하나가 더해진다.
- 응답 뒤 작업(`after()`)의 실패는 4b·4c·5a와 같이 기록하지 않는다. 남은 사본은 다음에 열 때 다시 찾는다.
- 실제 iPhone, Google OAuth, 호스팅, 운영 Supabase 설정은 검증하지 않았다.
