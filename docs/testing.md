# 테스트 지침

사용자가 Spring에서 사용하던 검증 방식을 Next.js API·Supabase 구성에 적용한다. 도구의 이름보다 계층의 책임, 실제 실행 범위와 테스트 데이터의 수명을 보존한다.

| 계층 | 검증 방식 | 책임과 정리 |
| --- | --- | --- |
| Domain | Vitest 순수 단위 테스트 | DB, 네트워크, React와 Next.js 없이 상태 전환과 규칙을 검증한다. 정상·실패·경계 조건에서 관찰 가능한 결과를 단언한다. |
| Persistence | 실제 테스트용 PostgreSQL/Supabase를 사용하는 저장소 통합 테스트 | 전체 웹 서버를 시작하지 않는다. 필요한 DB·저장 어댑터만 구성해 쿼리, 매핑, 제약조건, 마이그레이션과 적용 대상 권한 정책을 검증한다. |
| Service | 실제 저장소와 연결한 서비스 통합 테스트 | 테스트 전체를 트랜잭션으로 감싸 자동 롤백하지 않는다. 실제 저장 결과를 확인하고 `afterEach`에서 테스트 데이터를 삭제한다. 외부 쇼핑몰 등 독립 시스템은 명시적인 경계에서 대체한다. |
| 요청 처리 경계 | Vitest Mock 테스트, Given–When–Then | 서비스를 대체하고 요청 파싱, 검증, 인증 결과 처리, 응답 상태·본문과 오류 매핑을 검증한다. |
| HTTP API | 실행 중인 테스트 API에 실제 HTTP 요청 | 계약과 통합 동작을 검증한다. API 문서와 요청·응답 계약의 일치를 CI에서 검사한다. |
| 사용자 흐름 | Playwright | 브라우저 조작에서 화면 결과까지 PC와 모바일 크기에서 확인한다. |

Spring의 `@DataJpaTest`에 대응하는 범위는 persistence 슬라이스다. `@DataJpaTest` 자체도 필요한 Spring 컨텍스트를 올리므로, 여기서는 전체 애플리케이션을 시작하지 않고 저장 계층을 검증한다는 의도를 따른다. 실제 DB 동작을 인메모리 객체나 쿼리 Mock으로 대신 검증했다고 보고하지 않는다.

서비스 테스트의 정리는 `afterEach`에서 수행한다. 테스트 전용 DB 또는 격리된 스키마·데이터 범위를 사용하며, 외래키를 고려한 삭제 순서와 병렬 실행 격리를 둔다. 테스트가 실패한 경우에도 정리 훅이 실행되어야 한다. 운영 데이터에는 이 정리 경로가 접근하지 않는다. 제품 코드의 원자성을 위한 트랜잭션은 별도로 검증하며, 이 지침이 제품 트랜잭션을 금지하지 않는다.

동작 변경은 Red → Green → Refactor로 진행한다. Red는 환경이나 문법 오류가 아니라 요구 동작의 부재로 실패해야 한다. API 계약과 문서를 연결하는 도구는 API 구현 단계에서 선택하고, 문서만 별도로 수정해 계약 불일치를 숨기지 않는다.

현재 목업에는 Domain과 브라우저 계층만 구현되어 있다. 영구 저장·서비스·API 테스트는 해당 기능을 연결할 때 위 원칙으로 추가한다. 현재 검증의 실행 방법은 [verify-moti](../tools/verify-moti/SKILL.md), 결과는 [검증 기록](verification.md)에 있다.
